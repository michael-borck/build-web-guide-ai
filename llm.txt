# Preface 

## Why This Book Exists

Most web development books teach you technologies. This one teaches you to make technology decisions.

AI can write HTML, CSS, and JavaScript faster than you ever will. If your only skill is writing markup, you are competing with something that does not sleep. But if you can evaluate whether a client needs a WordPress site or a React app, explain why to a non-technical stakeholder, and direct AI to build it correctly, you have the skills that actually matter.

This book teaches web development as a business decision-making skill. Every chapter starts with the concept, not the code. You explore ideas through AI conversation before writing a single line. By the time you reach the syntax, you understand what it means and why it exists. That understanding is what lets you evaluate AI output, choose the right technology for the problem, and communicate your reasoning to people who do not write code.

The 2027 edition adds the practices around the build: specify what the client needs, write checks that run, and hand over a repository another person can maintain. An agent can produce a site from a sentence. It cannot know what the client meant, test it on a phone on a bus, or tell you whether it is any good. Those judgements remain yours.

The book covers the full spectrum of web decisions: hand-coded HTML/CSS/JavaScript for control, WordPress for rapid deployment, headless architecture for flexibility, React for modern applications. You learn when to use each one as well as how.

## If You Have Been Vibe Coding Websites

You may have already built a website by prompting AI. For a simple landing page or portfolio, that works. AI generates the HTML, you paste it into a file, it looks fine.

But as sites get more complex, questions arise that vibe coding cannot answer. Why does the layout break on mobile? Should this be a WordPress site or a custom build? How do I connect to an API without exposing credentials? Why is the page slow?

This book gives you a look under the hood. Through simple projects, you learn how the parts fit together: how HTML structures content, how CSS controls presentation, how JavaScript adds behaviour, how APIs connect to external data. That understanding makes you better at guiding AI, whether you continue vibe coding or move toward more intentional development.

If you are curious about what AI is actually producing, or if you have hit the point where prompting alone is not enough, this book is a good next step.

## Who This Book Is For

- Professionals who need to understand web development for their roles
- Career changers entering tech from business backgrounds
- Anyone who wants to build web solutions with AI as a partner
- People who need to evaluate web technologies, not just use them

No prior programming experience required. We start from scratch.

## What This Book Is Not

This is not a computer science textbook. It does not cover algorithms, data structures, or computational theory. It teaches you to build things for the web, with enough understanding to make good decisions about how.

It is not a framework-of-the-month guide. You will learn HTML, CSS, JavaScript, WordPress, and React, technologies chosen because they cover the spectrum from simple to complex and will remain relevant regardless of what is trending next year.

It is not a book that treats AI as a novelty. AI is your development partner throughout. The book teaches you to architect solutions that AI helps you build, evaluate AI output with professional judgement, and communicate requirements clearly enough for AI to be useful.

And it is not a book for people who want to become full-time frontend engineers. It is for people who want to understand web development well enough to lead projects, evaluate vendors, build prototypes, and make informed technology decisions in a business context.

## If You Are Feeling Uncertain

You do not need to be "technical" to build for the web. That word gets used as a gatekeeper, but the reality is that web development is a learnable skill, not a personality trait. If you can write a clear email, you can learn to write a clear prompt. If you can organise a spreadsheet, you can learn to structure a web page. This book starts where you are.

## How This Book Is Structured

The book progresses from foundations to full applications:

Part I: Your AI Development Partnership introduces how to work with AI effectively from day one.

Part II: The Practice Spine covers the practices that make an AI-built site trustworthy: specifying before you build, checks that run, and the agent-ready repo and handover. These are the working chapters for the 2027 edition. Read them when you are building, and return to them at handover.

Part III: Web Foundations covers web fundamentals using vanilla HTML, CSS, and JavaScript. No frameworks, no build tools. This is deliberate. Every framework, React included, ultimately produces HTML, CSS, and JavaScript that a browser renders. Understanding these fundamentals means you can debug anything built on top of them. It also teaches you to control AI. If you delegate a web project to AI without constraints, it will probably choose React, set up a build system, and produce something that works but that you cannot modify or explain. Part III gives you practice guiding AI within constraints, building the habit of directing rather than delegating.

Part IV: Content Management for Business moves to platforms: WordPress for rapid development, content management, and extending with plugins and themes.

Part V: Modern Frontend Development introduces React for component-based applications, headless architecture, and modern development patterns.

Part VI: The Professional Developer ties it all together: professional practices, emerging technologies, and building a development career.

This edition supports ISYS3004 Business Web and Mobile Technologies, S1 2027. The unit materials are the source of truth; this book is the reference. The 2027 course map appendix shows which chapters support each module.

Each chapter follows a consistent pattern:

1. Concept first. A real-world analogy before any code. Restaurant menus for HTML structure, café atmospheres for CSS, ordering systems for APIs.
2. AI exploration. Guided prompts where you explore the concept through conversation with your AI assistant. You build understanding before you build anything.
3. From concept to code. The simplest implementation that demonstrates the idea. No walls of syntax.
4. Business connection. Why this technology matters commercially. When to use it, when not to.
5. Practice and reflection. Exercises levelled from direct application to open-ended design challenges, plus journal prompts for deeper thinking.

# Understanding Your AI Web Development Partner 

## A New Way to Build for the Web

Right now, AI can write HTML, CSS, and JavaScript in seconds. It can create entire websites, debug code, and explain complex concepts. So why learn web development at all?

AI is fast at writing code, but it doesn't understand what your business needs. You're the architect, the translator between business requirements and technical solutions. AI is your highly skilled assistant who needs clear direction.

This book teaches you to be that architect.

## The Partnership Experiment

This experiment shows how AI works as a web development partner, and it will shape how you learn throughout this book.

### Round 1: The Vague Request

Open your AI assistant (ChatGPT, Claude, or whatever you're using). Type this exactly:

Make a website

What did you get? The AI probably asked questions or made assumptions. This is your first lesson: AI needs direction.

### Round 2: The Simple Request

Now try:

Make a business website

You likely got a massive amount of HTML, CSS, maybe JavaScript: a complete but generic template. This is AI's default: give you everything at once.

### Round 3: The Learning Request

Now try:

I'm learning web development. Show me the absolute simplest HTML page that displays a business name and tagline. Nothing else.

You might get:

text
Explain how a web page is structured, using a building analogy, before showing any code

Now you're using AI to build understanding as well as generate code.

## What This Experiment Teaches Us

1. AI defaults to complexity: it assumes you want a "complete" solution
2. Your prompts shape your learning: clear learning goals get clearer responses
3. Concepts before code: you can use AI to understand ideas before syntax
4. You're in control: AI follows your lead, not the other way around

## The Three Learning Strategies

Throughout this book, we'll follow three core strategies:

### Strategy 1: Understand the Concept Before the Code

Every web development task follows patterns. Understand the pattern first, then learn how HTML/CSS/JavaScript expresses it.

Example: Don't ask "How do I make a navigation menu?" Instead, ask "What is the purpose of navigation on a website?" Then, "Show me the simplest HTML navigation."

### Strategy 2: Use AI to Explore, Not to Avoid Learning

AI is your exploration tool. Use it to:

- See different approaches to the same problem
- Understand why code works
- Compare technologies
- Debug your understanding

### Strategy 3: Build Mental Models, Not Just Working Websites

Aim to understand how and why a website works, and use AI to build those mental models.

Example: Ask "Draw a diagram showing how HTML, CSS, and JavaScript work together" or "Explain responsive design using a newspaper analogy."

## How AI Thinks vs How Developers Think

### AI Thinks in Patterns

- It has seen millions of websites
- It pattern-matches to give you a "typical" solution
- It doesn't understand your specific business context
- It can't know what you don't know yet

### Developers Think in Problems

- What exactly needs to be solved?
- Who is the user?
- What's the simplest solution?
- How will this be maintained?
- What could go wrong?

Your job is to bridge this gap: Think like a developer, then guide AI to help you implement.

### Part I (Your AI Development Partnership): AI as Partner

Example prompts:

Example prompts:

# Specify Before You Build 

An agent will build whatever you describe, including the parts you did not mean. Give it a sentence and it fills the gaps with the most common pattern it has seen. That pattern might be a carousel, a contact form, three pricing cards, or a stock photo of strangers laughing at a salad. The agent is doing what the brief allows.

Maria's first email contains one sentence of need wrapped in a launch date. The distance between that email and a working site is where projects succeed or fail. This chapter is about closing that distance before the build starts.

## The Concept First

A specification is a written contract for a build. It records who the site serves, what those people need to do, what content exists, which design decisions are fixed, what counts as done, and what is excluded. You write it before the build and use it during the build. When the client asks for a change, the spec tells you whether the change is inside the agreement or a new request.

A wish list has a different job. It records what the client likes. A contract records what the build must do.

| Wish list | Contract |
|---|---|
| A gallery | Six photos, owned by Maria, each with alt text, on the home page |
| Mobile friendly | At 375px, no page scrolls horizontally and the booking action is visible without scrolling |
| Easy to update | Dev can update the menu in under five minutes without editing code |
| Professional | Brand palette and type scale applied, no stock photos, hours correct on every page |

A contract can be tested. A wish can only be discussed.

The test of a spec is direct. Give it to a builder who has never met the client. If that builder produces something the client would accept, the spec did its job. If the builder has to ask what the client meant, the spec has a gap.

## Understanding Through a Renovation Brief

A cafe renovation has the same problem. The owner says she wants the room to feel warmer. The builder can install a heater, paint a wall, or add lamps. All three might make the room warmer. None of them can be accepted or rejected against the word "warmer" alone.

A useful renovation brief says which walls are moving, which lights are being replaced, which finishes are approved, which parts of the room stay, and what the client will inspect before paying. The builder still makes design decisions. The brief sets the boundaries those decisions must respect.

A web spec works the same way. "Make it professional" is the feeling. "Brand palette, type scale, six photos, booking action above the fold at 375px, hours correct on every page" is the brief. The first gives the agent room to invent. The second gives the agent a standard to meet.

## A spec sets the boundary
You do not need to tell the agent which HTML element to use. You need to tell it what the result must do. The boundary is the contract. The implementation is the agent's job.

## The Client's Brief

This is Maria's email. It is the brief that starts the client project.

> From: Maria
> To: Contractor
> Subject: Website for the new place
>
> Hi,
>
> We're opening the [suburb] store and I need a website. Nothing fancy. People
> should be able to find us, see the menu, and book a table. That's it.
>
> My nephew did one for his mum's salon in an afternoon with one of those AI
> things, so I don't think this is a big job. I've told the local paper we launch
> on [date]. Can you make that?
>
> I'll send you the logo and a few photos. Dev has the menu.
>
> Thanks,
> Maria

The brief gives you a purpose, a rough scope, a launch date, and a budget signal. It does not give you the things a builder needs.

It does not say who updates the menu, how often the menu changes, which device customers use, what "book" means, what happens after a booking, which content is current, or what "professional" looks like. It does not say what Maria would drop if the date slipped. It does not say how the site connects to the phone bookings the cafe already takes.

None of these gaps are Maria's fault. She is describing her business. She is not writing a technical document. Your job is to ask.

## Do not fill a gap with a guess
A guess in the spec becomes a defect in the build. Write the question down. Ask the person who knows. "I assumed" is not a requirement.

This chapter uses Harbour & Hearth Northbridge as a teaching example. Your fact sheet and interviews are the source of truth for your own franchise. Do not copy the example's content into your assessment. The method is the same.

## Working with Your AI Partner

AI is useful in three places in this chapter. It can find the gaps in a brief, role-play the people who know the answers, and test whether a criterion can be read two ways. AI is a poor tool for writing the spec. The spec records your judgement, and your judgement is what your assessment rewards.

### Exploration 1: Find the Gaps Without Filling Them

Paste Maria's email and ask for questions. Do not ask it to answer them.

Ask your AI:
Here is a client email. List every question you would need answered before
you could build the site. Do not answer the questions. Group them by the
person most likely to know: the owner, the office manager, the customer,
or the IT vendor.

A useful answer will include questions about content ownership, update frequency, devices, the booking process, brand assets, hosting, and what happens when the site is wrong. If the AI starts answering its own questions, stop it. You want the gaps. Plausible filler hides them.

### Exploration 2: Interview a Persona

A client simulator uses one persona per conversation. You can do the same with any AI tool.

Ask your AI:
Role-play Dev, the office manager at Harbour & Hearth. I am the
contractor for this franchise. Answer only from the fact sheet I
provide. Do not volunteer information. If I ask a vague question, give
a vague answer. If I ask about your work, answer as someone who updates
the menu and hours.

Fact sheet:
[paste your fact sheet here]

Then ask Dev what changes, how often, and who does it. Ask what changes in a normal week, and what catches her out. Ask what she would stop using the site over. The requirements that matter usually sit inside those answers. A feature list hides them.

### Exploration 3: Test a Criterion for Ambiguity

Take a weak criterion and ask the AI to build two different sites that would both pass it.

Ask your AI:
Read this acceptance criterion: "The site is easy to use on a phone."
Describe two different websites that would both pass it. Then tell me
which words are doing too much work.

The answer should expose the problem. "Easy" has no observable result, and "phone" does not name a screen width, a device, or a context. A criterion that allows two unrelated builds cannot settle a disagreement.

## From Brief to Spec

A practical spec template has seven parts, plus a log for the replication test. Each part answers a question a builder would otherwise have to guess.

```markdown
# Spec: Harbour & Hearth Northbridge

Version: v1
Client: Maria, owner; Dev, office manager
Last replication test: v1

## Purpose

## Users and top tasks

## Content

### Content model

### Design tokens

## Must / Should / Won't

## Constraints

## Acceptance criteria

## Out of scope

## Replication test log
### Purpose

Write one or two sentences from the client's point of view. Name the audience, the job and the outcome. Leave out the technology.

> Let local customers find the current menu, hours and booking action on a phone, and let Dev update the menu without calling the contractor.

Three requirements are carried in those two sentences. "Current" carries the weekly update. "On a phone" carries Sam's context. "Without calling the contractor" carries Dev's constraint. The purpose does not mention a framework, a plugin, or a page count.

### Users and Top Tasks

Define users by what they need to do. Age and job title say less than context. Include the people inside the business. Maria pays for the site, but Sam uses it. Both belong in the spec.

| User | Task | Device and context |
|---|---|---|
| Local customer | Find the current menu and hours | Phone, on the bus, often one-handed |
| Local customer | Book a table | Phone, about 30 seconds, possibly poor signal |
| Dev | Update the menu and opening hours | Desktop, during the working week, no code |
| Maria | Check that the site looks professional and current | Phone, in the store, between customers |
| Alex | Keep the site maintained | Occasional, remote, low tolerance for plugin sprawl |

The context column changes the requirement. A booking at a desk with a fast connection is a different task from a booking on a bus with one bar of signal. The first can tolerate a long form. The second cannot.

### Content and the Content Model

Content is what the site says. A content model is what the client edits.

Start with the content the business already has: the menu, the hours, the photos, the staff bios, the contact details. For each item, ask who owns it, how often it changes, which fields it needs, and where it appears.

| Content type | Fields | Owner | Changes | Appears on |
|---|---|---|---|---|
| Menu | Sections; item name, description, price, dietary tags | Dev | To confirm in the interview | Menu, Home |
| Opening hours | Day, open, close, note | Dev | Rarely; public holidays | Home, Contact, Footer |
| Booking enquiry | Name, phone, party size, date, time, notes | Front of house | Per booking | Booking page, staff inbox |
| Photo | Image, alt text, caption, credit | Maria | Occasionally | Home, About |
| Promotion | Title, dates, image, link | Maria | Occasionally | Home |
| Site details | Address, phone, email, social links | Dev | Rarely | Everywhere |

Maria says "see the menu". The brief does not say how often the menu changes or who updates it. The content model forces those questions. A spec that records "to confirm" is more honest than one that guesses. The interview replaces the placeholder with a frequency and an owner.

A content model is not a database schema. It is a list of the things the client edits and the fields each thing needs. You will meet the same idea in WordPress as custom post types and fields ().

Every field needs a reason. If nobody can say where a field appears or who changes it, remove it. A content model with twelve fields Dev never fills is a maintenance cost disguised as thoroughness.

### Design Tokens

Maria wants the site to look professional and warm, and she does not want it to feel corporate. That is a direction. A builder cannot apply it consistently without decisions. Design tokens turn the direction into named values.

Tokens are the small set of decisions that every page reuses: colour roles, typefaces, type scale, spacing, radius, borders, shadows, motion and focus. A first set for Northbridge might look like this.

| Token | Value | Rule |
|---|---|---|
| `--colour-ink` | `#2b2118` | Body text. At least 7:1 contrast on `--colour-paper` |
| `--colour-paper` | `#f7f1e7` | Page background |
| `--colour-accent` | `#b4552d` | Primary action only. At least 4.5:1 with white text |
| `--font-display` | Fraunces, Georgia, serif | Headings |
| `--font-body` | Source Sans 3, system-ui, sans-serif | Body text |
| `--space-1` to `--space-6` | `0.25rem` to `1.5rem` | A spacing scale; every gap uses one of these values |
| `--radius` | `4px` | Buttons, cards, images |
| `--focus-ring` | `3px solid #1f5c99` | Every interactive element |

```css
:root {
  / Colour roles. Pages refer to the role, not the hex value. /
  --colour-ink: #2b2118;
  --colour-paper: #f7f1e7;
  --colour-accent: #b4552d;
  --font-display: "Fraunces", Georgia, serif;
  --font-body: "Source Sans 3", system-ui, sans-serif;

  / Spacing scale. Every gap uses one of these values. /
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-6: 1.5rem;
  --radius: 4px;
  --focus-ring: 3px solid #1f5c99;
}

The spec names the roles and the constraints. The build applies them.  shows how CSS uses tokens; this section is about deciding them before the agent starts.

Contrast belongs in the token decision. A warm accent that fails contrast is not usable for text, however good it looks in the brand guide. Two font families are also a performance decision. If the brand allows, use one family and a system fallback.

### Must, Should and Won't

Priorities are how a spec survives a bad week. If everything is a must, the first slip becomes a negotiation about everything.

| Priority | Meaning | Northbridge examples |
|---|---|---|
| Must | Without it, the site fails its purpose | Current menu, correct hours, booking action at 375px, Dev can update the menu, brand palette and type |
| Should | Valuable, and can slip without breaking the contract | Six photos, a short story, a live music section, a map embed |
| Won't | Explicitly excluded from this version | Online payments, customer accounts, a native app, a loyalty scheme, a blog, online ordering |

The stakeholders disagree. Maria wants a gallery first. Sam wants the booking action first. Dev wants the menu to be correct. Alex wants fewer parts that can break.

The spec resolves the disagreement in writing. Booking is a Must because Sam will not complain twice. The menu update is a Must because a wrong menu loses trust. The gallery is a Should, limited to six photos owned by Maria, with no third-party gallery plugin. Maria gets the look she asked for, Sam gets the booking action, Dev gets a maintenance load she can carry, and Alex gets one less plugin to update.

Record the decision and the rejected option in `DECISIONS.md`. The spec says what will be built. The decision record says why this option was chosen and what it cost.

### Constraints

Constraints are requirements that limit the solution.

| Constraint | Why it exists | What it forces |
|---|---|---|
| Plain HTML, CSS and JavaScript | Static site scope | No framework, no build step |
| Works from 375px | Sam books on a phone | Layout and type are tested at 375px |
| WCAG 2.2 AA | Public site, low-vision user | Contrast, focus, headings, alt text, target size |
| No paid tools | Unit budget | Free hosting and open fonts only |
| Static hosting | No server to maintain | Booking is an enquiry. Staff confirm it later |
| Launch date | Maria's newspaper promise | Scope can shrink; Must items cannot |

Constraints can conflict. A static site cannot confirm a booking without a server. The spec has to say what "book" means, or the build will invent a confirmation the business cannot honour.

### Acceptance Criteria

An acceptance criterion is a statement about the build that a person can mark pass or fail. It describes an observable result and the condition under which it must hold. Write criteria for the Must items. A criterion that cannot fail is not a criterion.

| Test | Question | Weak example | Why it fails |
|---|---|---|---|
| Observable | Can you see the result? | Looks professional | No observable result |
| Specific | Does it name one condition? | Works on mobile and desktop | Two conditions, neither defined |
| Implementation-free | Does it allow any suitable build? | Uses a hamburger menu | Names a solution |
| Decidable | Would two reviewers agree? | Easy to use | Depends on the reviewer |

These criteria pass all four tests:

| Acceptance criterion | How it is checked |
|---|---|
| A customer can see today's opening hours on the home page at 375px without scrolling. | Open the home page at 375px. Compare the hours with the fact sheet. |
| A customer can start a booking enquiry from any page in one tap, and the form asks for party size, date and time. | Visit each page at 375px. Count the taps to the form. Check the fields. |
| Dev can update the menu in under five minutes without editing code. | Time Dev doing it with the agreed fields. |
| Every page has one `h1` and a logical heading order. | Read the heading outline for each page. |
| Every interactive element has a visible focus ring of at least 3px. | Tab through each page and watch the focus indicator. |
| The booking action is visible at 375px without horizontal scrolling. | Open each page at 375px. Check for horizontal scroll and the action's position. |

A useful pattern is a person doing a task, under a condition, with an observable result. The pattern is a guide. Do not apply it as a formula. Some criteria describe a property of the whole site, such as heading order or contrast.

One criterion can need several checks. "No horizontal scroll at 375px" is one criterion. The check might visit every page and every interactive state.  introduces checks; the next practice chapter turns criteria into checks that run.

Six to ten criteria are enough for a static client site. Thirty criteria become a document nobody checks. Add a criterion when a real defect appears. Do not add one because the list looks thin.

Acceptance criteria also protect the client. Maria can reject a build that misses a Must criterion. She cannot reject a build for failing a feeling she never defined.

## A criterion can expose a stack limit
A static site cannot give Dev a full content management screen. If a Must criterion needs one, the spec and the build disagree. Record the gap in `CRITIQUE.md`, agree with the client whether it is a Must for this version, and carry the requirement into the content-managed version. Do not drop it without recording the decision.

### Out of Scope, Assumptions and Change

Out of scope protects the launch. It names what a reasonable person might expect but this version will not do.

For Northbridge: online payments, customer accounts, a native app, a loyalty scheme, a blog, online ordering, and multi-language content.

Assumptions are facts you need but do not control. Write them down.

- The brand office supplies the logo and palette before the build starts.
- Dev supplies the menu in the agreed fields. A photo of the chalkboard is not enough.
- The host supports a static site and a form endpoint.
- Booking is an enquiry. Staff confirm by phone.
- Maria can approve content within two working days.

If an assumption fails, the spec changes. Writing it down makes the change visible.

A change clause keeps the contract usable after sign-off.

> A change that adds a Must item, a page, or a content type is a change request. Record it in `DECISIONS.md`, update the spec version, and re-run the replication test if it changes a Must criterion.

Version the spec. Use v0 after the first brief, v1 after the interviews and the replication test, and v1.1 after a material change. The version number is evidence of what was agreed.

## The Failure: Describing the Current Build

The most common bad spec is an accurate description of the site you already have.

| Describes the build | Describes the client's need |
|---|---|
| A hero carousel with three slides | A first-time visitor can tell what the business is and whether it is open now |
| A sticky navigation bar with a hamburger menu | A phone user can reach the menu and the booking action from any page in one tap |
| A grid of six menu cards with hover effects | Dev can publish the menu without calling a developer |
| A contact form with name, email and message | Sam can request a table for four on Friday at 7pm and knows what happens next |

The drift happens in four steps. The agent builds something. It looks complete. The spec is rewritten to match it. The spec now passes the replication test because it describes what the agent already built. The client's need is still unmet.

The spec has become a receipt. It records what was bought. The requirement is missing.

Use one question to separate the two.

> If the build disappeared, would this sentence still tell a new builder what the client needs?

"The site has a hero carousel with three slides" fails. Delete the build and the need disappears with it. "A first-time visitor can tell whether the cafe is open now and start a booking in one tap" passes. It still describes the client's need when no build exists.

The build is evidence. The spec is the standard the evidence is judged against.

Agents default to the common pattern. If the spec says "menu", the agent builds a static menu. If it says "booking", the agent builds a contact form. The agent is filling a gap with the average of the web. The gap is yours to close.

### A Worked Failure

The first `SPEC.md` for Northbridge said: "The site must be responsive."

The agent produced a desktop layout that shrank. At 375px the booking button sat below three screens of gallery. The student asked the agent to "make it more mobile". The next build moved the button. The booking form was still a general contact form, and the gallery still autoplayed.

The agent's CSS was not the main problem. The spec had no criterion for the booking action at 375px and no rule for the gallery's motion. The fix was two sentences in the spec. A longer chat would not have helped.

Change the spec, then rebuild. A chat fix disappears when the session ends. A spec fix survives the next agent, the next developer and the handover.

## The Replication Test

The replication test measures the spec. It does not measure the agent.

You give the spec alone to a fresh agent and measure the gap between what the spec says and what the client needs. The agent reads the spec as a stranger would. If the reader has to guess, the spec is incomplete.

### The Procedure

| Step | What to do |
|---|---|
| 1. Freeze | Commit `SPEC.md` and note the version. |
| 2. Start fresh | Open a new agent session and an empty folder outside your repo. |
| 3. Remove context | Do not show the agent your site, your screenshots, your repository or your earlier chat. |
| 4. Give the spec | Provide `SPEC.md`, the fact sheet and the fixed constraints. |
| 5. Build without coaching | If the agent asks a question the spec answers, answer from the spec. If the spec does not answer it, record the question and tell the agent to use its judgement. |
| 6. Compare | Judge the replica against the acceptance criteria. Your site is not the standard. |
| 7. Classify | Label each gap: missing, ambiguous, unstated constraint, or builder error. |
| 8. Revise | Change the spec, not the chat. Bump the version. Run again if time allows. |

The comparison grid is the acceptance criteria. A replica that looks different can still pass. A replica that looks similar can still fail a criterion.

### A Worked Replication Test

The v1 spec produced a plausible home page, a menu page, a contact form, and a three-slide autoplay gallery. The first impression was good. The criteria told a different story.

| Acceptance criterion | Replica result | Gap type | Spec change |
|---|---|---|---|
| Menu items show dietary tags | No dietary tags on any item | Missing | Added dietary tags to the menu fields |
| Booking asks for party size, date and time | Contact form with name and message | Ambiguous | Defined booking as an enquiry and listed its fields |
| Opening hours include public holiday notes | Hours table omits public holidays | Missing | Added a note field and named the fact sheet as the source |
| Booking action visible at 375px | Button below the gallery | Ambiguous | Added "visible without scrolling at 375px" |
| Every interactive element has visible focus | No focus styles | Missing | Added the focus token and a criterion |

Each gap in the table was a spec problem. The replica did what the spec allowed.

The gallery deserves a second look. Maria asked for a gallery. The spec did not say how many photos, who owns them, or whether they may autoplay. The agent chose the common pattern: three slides, automatic movement, no pause control. The fix belongs in the spec. Complaining about the agent's taste changes nothing.

### Classifying the Gap

| Gap type | Meaning | What to change |
|---|---|---|
| Missing | The spec never said it | Add the requirement or criterion |
| Ambiguous | The spec allowed two readings | Define the term and add a condition |
| Unstated constraint | The spec assumed something outside the builder's control | Add the assumption and its consequence |
| Builder error | The spec was clear and the replica ignored it | Keep the spec; add or strengthen a check |

Only the first three lead to a spec change. A builder error is still useful evidence. It tells you which criteria need a check that runs.

### What Counts as a Pass

A pass means every Must criterion is met, and no gap depends on knowledge that only you have. Two good builders will differ in details and agree on the contract. That is a pass.

Do not score the replica out of ten. A number hides which criterion failed and why. Record the biggest gap, the gap type, and the sentence you added.

### Limits of the Test

Treat one run as a sample. The same agent family may share the same blind spots, so use a different tool when you can. The replica may be better than your build in one place; copy the better idea or record why you rejected it. The test does not replace client review. It tests whether the spec communicates the client's need.

The test takes about 25 to 30 minutes. Run it when a Must criterion changes. Do not run it after every commit.

## Keep the replica
Keep the replica folder and the gap table. They are evidence for the assessment conversation, and they show the spec improving across versions. A spec that never failed a replication test has probably never been tested seriously.

## Building Your Mental Model

### The Artefacts

| File | Question it answers | Written when |
|---|---|---|
| `SPEC.md` | What does the client need, and what counts as done? | Before the build |
| `DECISIONS.md` | Which option did we choose, and what did we reject? | During the build |
| `CRITIQUE.md` | What is still wrong or unverified? | After the build |
| `checks/` | Does the build still meet the criteria? | During and after the build |

These artefacts answer different questions. None of them is an essay. The spec sets the standard. `DECISIONS.md` records the trail, `CRITIQUE.md` records the honest gap, and the checks provide evidence.

### The Loop

client need
    |
    v
  SPEC.md ------------> build ------------> checks
    ^                                        |
    |                                        v
    +-------- replication test <-------- CRITIQUE.md

The replication test is the arrow that returns to the spec. It is the feedback loop that most projects skip.

### The Readers

| Reader | What they need from the spec |
|---|---|
| Maria | Scope, cost, what she will get, and what she will not |
| Dev | Content fields, update effort, and who owns each item |
| Alex | Maintenance load, hosting constraints, and plugin count |
| The builder | Tasks, constraints, and acceptance criteria |
| The checker | Criteria that can become checks |

If one reader cannot answer their question, the spec is incomplete for that reader. The client, the content owner, the maintainer, the builder and the checker need the same decisions, even when they need different documents.

### The One-Page Test

Can a stranger answer these five questions from the spec alone?

1. Who is the site for?
2. What must each person be able to do?
3. What content exists, and who changes it?
4. What does done look like?
5. What is excluded?

If any answer is missing, the spec is not ready for a replication test.

## Business Applications

A spec is a quoting tool. A fixed-price quote without one is a guess. With one, the vendor prices the Must items, lists assumptions, and states what a change will cost.

It also controls change. The out-of-scope list turns "can you just add online ordering" into a conversation about budget and date. The change clause gives both sides a procedure.

The same document supports handover. The next developer can rebuild or maintain the site without your chat history. A replication test is part of the handover. It shows whether the written record is enough for a stranger.

The cheapest time to find a missing requirement is before the build. The assessment conversation is an expensive place to discover it. The replication test is a pre-mortem with a stopwatch.

For AI projects, the spec is the difference between directing an agent and discovering what it decided. The agent can produce a site in an afternoon. The spec decides whether that site is the one the client needed.

# Checks That Run 

The agent says the site is done. The page looks right on your laptop. A customer opens it on a phone and cannot find the booking button. Nothing in the build failed. No one had written a check for that.

A check is how you turn "it looks fine" into evidence. It is also how you stop the same defect from returning next week.

## The Concept First

A check is a claim about the build that can fail. A manual check is a person looking. A check that runs is a command that repeats the same judgement every time. The command gives you evidence you can show. The person gives you an opinion you have to trust.

A check does not prove the site is good. It proves that one claim held under one set of conditions. That is enough to catch regressions, and not enough to sign off the site.

## A check is evidence only if it can fail
If a check passes on a broken page, it is not testing the thing you care about. Before you trust a check, break the page on purpose and watch the check fail.

## Understanding Through a Fire Drill

A fire drill tests whether the alarm sounds and the exits open. It cannot tell you whether the exit sign points the right way.

Automated checks are the drill. They test specific paths under specific conditions. They run every time, and they only test what someone thought to test. The exit sign still needs a person to look at it.

Tools catch a useful subset. You decide what the subset means, and you check the rest yourself. The rest of this chapter shows how.

## The Four Principles

WCAG organises accessibility under four principles: Perceivable, Operable, Understandable, Robust. The principles give a person a checklist and give the tools a map.

| Principle | Question | Northbridge example |
|---|---|---|
| Perceivable | Can everyone perceive the content? | The menu photo has alt text that describes the dish, not "image". |
| Operable | Can everyone operate it? | The booking button can be reached by keyboard and has a visible focus ring. |
| Understandable | Can everyone understand it? | The form says "Party size" and explains what happens after submission. |
| Robust | Does it work with different browsers and assistive technology? | The form uses a real `button` and `label`, not a clickable `div`. |

The principles are not a score. A page can pass a tool and still fail a person. The tool checks a rule. The principle asks whether the page works.

## What the Tools Catch

A practical check suite uses four tools. Each one looks at a different layer.

| Tool | What it checks | What it misses |
|---|---|---|
| html-validate | HTML structure, duplicate IDs, invalid nesting, some missing attributes | Whether the content is meaningful |
| axe | A subset of WCAG A and AA: contrast, labels, roles, names, some heading order | Whether alt text is meaningful, whether the heading order makes sense, whether the copy is clear |
| Playwright | Behaviour, layout, keyboard access, responsive layout, API failure | Whether the behaviour is right for the business |
| Lighthouse CI | Performance, accessibility score, best practices, budgets | Whether the site is usable on a cheap phone with a cracked screen, whether the data is correct |

The tools overlap, which is useful, and they share blind spots.

| Command | What it runs |
|---|---|
| `npm run validate` | `html-validate` over `site/` |
| `npm test` | Playwright checks in `checks/` and `tests/` |
| `npm run lighthouse` | Lighthouse CI |
| `npm run check` | validate, secrets and Playwright |

Use `npm run check` before you commit. Run `npm run lighthouse` when you change images, fonts or layout.

An axe check looks like this:

```js
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('home page has no detectable WCAG A/AA violations', async ({ page }) => {
  await page.goto('/');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
    .analyze();
  expect(results.violations).toEqual([]);
});
The check reports detectable violations. It does not tell you whether the page is accessible.

### What No Automated Check Can See

- Whether alt text describes the image.
- Whether the heading order helps a person navigate.
- Whether the copy is clear.
- Whether the booking flow matches the business process.
- Whether the site works on a slow connection.
- Whether the data is correct.
- Whether the user can recover from an error.

These are not edge cases. They are the parts of the experience that decide whether the client keeps the site.

## A passing axe run is not an accessibility sign-off
axe can find a missing `alt` attribute. It cannot tell you whether the `alt` text says anything useful. It can find a missing label. It cannot tell you whether the label uses words the customer understands.

## From Criterion to Check

The check starts with the acceptance criterion, not the code. If the criterion is vague, the check will be vague.  gave you the criterion, and a check turns it into evidence.

A useful check has four parts:

1. The condition. A viewport, a page, a network response, a keyboard action.
2. The action. What the user or the test does.
3. The observable result. What must be true.
4. The failure message. What the output says when it is false.

If one part is missing, the check is weak. A check that says "the page works" has no condition and no observable result.

### Example: The Booking Action at 375px

The criterion is: "The booking action is visible at 375px without scrolling."

A weak check looks for the viewport meta tag. The tag is a proxy. A page can have the tag and still overflow.

js
import { test, expect } from '@playwright/test';

test('booking action is visible at 375px', async ({ page }) => {
  await page.goto('/');
  const cta = page.locator('[data-cta="primary"]');
  await expect(cta).toBeVisible();

  const box = await cta.boundingBox();
  const viewport = page.viewportSize();
  expect(box.x).toBeGreaterThanOrEqual(0);
  expect(box.x + box.width).toBeLessThanOrEqual(viewport.width);
});

test('no horizontal scroll at 375px', async ({ page }) => {
  await page.goto('/');
  const overflows = await page.evaluate(
    () =>
      document.documentElement.scrollWidth >
      document.documentElement.clientWidth
  );
  expect(overflows).toBe(false);
});
The first check is not useless. It catches a missing tag. It does not catch the defect the customer reported.

`toBeVisible()` is stronger than `toBeAttached()`. An element can be attached to the page and still sit outside the viewport. The customer cannot see it, and the weak check goes green.

### Example: Every Page Has a Title

The criterion is: "Every page has a non-empty title."

```js
import { test, expect } from '@playwright/test';
import { readFileSync } from 'node:fs';

const pages = JSON.parse(
  readFileSync(new URL('../pages.json', import.meta.url), 'utf8')
);

for (const path of pages) {
  test(`${path} has a non-empty title`, async ({ page }) => {
    await page.goto(path);
    expect((await page.title()).trim().length).toBeGreaterThan(0);
  });
}

The check is only as good as the page list. If a page is missing from `pages.json`, the check will not visit it. Review changes to `pages.json` as carefully as changes to the site.

### Example: The API Failure

The criterion is: "When the live data request fails, the page shows a friendly message and a way to retry."

The happy path is easy to check. The unhappy path is the one that protects the customer.

text
Ask your AI:
Here is an acceptance criterion: "The booking action is visible at 375px
without scrolling." Write the smallest Playwright check that would fail
if the criterion were false. Then name one thing the check cannot see.
Do not change the site.

Read the check before you run it. Does it test the outcome or a proxy? Does it use a role or a brittle selector? What happens if the button is attached but off-screen? Improve the check before you trust it.

### Exploration 2: Ask How the Check Could Be Gamed

Ask your AI:
Here is a passing check. Show me three ways to make it pass without
fixing the page. For each one, explain what it hides from the customer.

The answer is a catalogue of the shortcuts in the next section. Do not apply them. Use them to recognise the diff when an agent does.

### Exploration 3: Find the Proxy

Ask your AI:
Here is a check. Is it testing the outcome or a proxy? Describe a page
that would pass the check and still fail the user.

A good answer names the gap between the assertion and the experience. That gap is why the manual check still exists.

## The Failure: The Agent Games the Check

An agent asked to make a check pass has three options. It can fix the site, weaken the check, or hide the problem. It will often choose the cheapest path that produces green. The agent is not malicious. It is optimising for the signal you gave it.

Your job is to make sure the green means something.

Each common shortcut below is a diff to read. The output alone is not enough.

### Weakening the Assertion

```diff
- await expect(page.locator('[data-cta="primary"]')).toBeVisible();
+ await expect(page.locator('[data-cta="primary"]')).toBeAttached();
`toBeAttached()` passes when the element is in the DOM. It can be off-screen, covered, or invisible. `toBeVisible()` tests what the customer can see.

diff
- test('no horizontal scroll at 375px', async ({ page }) => {
+ test.skip('no horizontal scroll at 375px', async ({ page }) => {
A skipped check is a green check that tests nothing. Read the output for `skipped` as well as `passed`.

### Hiding the Problem

```diff
- Book a table
+ Book a table

The button is now hidden from screen readers. A sighted user can still click it. A screen reader user loses the action. A visibility check may pass because the page still renders. If the suite runs axe, this may be caught. If it only checks visibility, it will not. The customer is worse off.

`aria-hidden` is not a fix for a duplicate control or a confusing label. It is a way to remove content from the accessibility tree. Use it for decorative content. Do not use it to hide content from a check.

### Hiding the Symptom

```css
body {
  overflow-x: hidden;
}
This clips the horizontal scroll. The fixed-width element is still there. The customer can still lose content off the edge. Find the fixed width, the image, or the grid that causes the overflow.  covers the common causes.

### Editing the Page List

A failing page is removed from `pages.json`. The checks visit fewer pages. The suite goes green.

Review `git diff pages.json` after every agent change. The page list is part of the test surface.

### Waiting for Luck

```js
await page.waitForTimeout(2000);

A fixed wait can make a flaky check pass once. It slows the suite and hides the race. Use a web-first assertion such as `await expect(locator).toBeVisible()`. Let the tool wait for the condition. A fixed delay only guesses how long that takes.

### How to Catch a Shortcut

- Read the diff as well as the green output.
- Run `git log --oneline -- checks/`.
- Make the check fail on purpose before you trust it.
- Ask the agent for the command and the output.
- Review changes to `pages.json`.
- Check that the assertion names the observable result.

## Git Evidence

The provided checks are a contract. The project template puts them in `checks/`. Your own checks go in `tests/`.

The history should show one commit for the provided checks: the commit that added the template. Run:

```bash
git log --oneline -- checks/
If there is a second commit, read it. If it edits a check, the checks were weakened. Revert the change, then fix the site. Record what happened in `DECISIONS.md`.

```bash
git checkout  -- checks/

The commit hash is the one that added the checks. If you are unsure, ask the agent to show `git log -p -- checks/` and read the diff before you revert.

A check is evidence only if the check itself is trustworthy. The git history is how you prove that the provided checks were not weakened.

A provided check can be wrong. If you believe it is, do not edit it. Record the problem in `CRITIQUE.md`, show the evidence, and ask for a decision. The default is to fix the site.

## A Worked 375px Audit

The site passes the desktop checks. The booking page looks fine on a laptop. At 375px, the page scrolls sideways and the booking button sits off-screen.

The existing check looks for the viewport meta tag. It passes. The customer still cannot book.

1. Open the site at 375px. Record the defect in `CRITIQUE.md`.
2. Write the outcome check. It fails.
3. Find the fixed width. It might be a hero image, a grid, a table, or a container with a hard-coded `width`.
4. Fix the cause. Do not add `overflow-x: hidden`.
5. Run the check again. It passes.
6. Add the criterion to `SPEC.md` if it was missing. The check and the criterion should point at each other.

The audit is not finished when the page looks better. It is finished when the check would catch the defect if it returned.

## A Worked API Failure

The live data widget shows opening status, today's specials, or another small piece of business data. When the API is up, the widget looks fine. When the API fails, the widget is blank.

The happy-path check passes. The unhappy path has no check.

1. Mock a 500 response in a Playwright test.
2. Assert that the page shows a friendly message.
3. Run the check. It fails because the page has no error state.
4. Add the error state. Add a loading state and an empty state while you are there.
5. Run the check again. Then run the happy path again.
6. Record the decision in `DECISIONS.md` and the remaining gap in `CRITIQUE.md`.

The check does not prove the API will never fail. It proves the page does something useful when it does.

## Building Your Mental Model

### The Check Pyramid

performance and budgets      Lighthouse CI
behaviour and layout         Playwright
accessibility                axe
structure                    html-validate

Start at the bottom. A page with invalid HTML is harder to check. A page with no accessible names is harder to use. The layers catch different defects. None of them is enough alone.

### The Criterion Chain

criterion -> condition -> action -> observable result -> assertion -> failure message

If the chain breaks at the condition, the check tests the wrong thing. If it breaks at the observable result, the check tests a proxy. If it breaks at the failure message, you will not know what failed.

### What the Check Proves

| The check proves | The check does not prove |
|---|---|
| One claim held under one condition | The site is good |
| The defect is gone for that path | The defect is gone everywhere |
| The page handles a mocked failure | The real API works |
| The element is in the viewport at 375px | The page is usable on a cheap phone |
| The provided checks were not edited | The student understood the check |

## Business Applications

Checks reduce rework. A defect caught before the client sees it costs minutes. A defect caught after launch costs trust, support time and sometimes revenue.

A fixed-price quote is easier to defend when you can name what you will verify: the booking action at 375px, the error state, the page titles, the contrast. The client knows what "done" includes.

The checks are also handover evidence. The next developer can run the suite before changing anything. They do not have to trust a chat log or a colleague's memory.

For AI projects, the suite is the defence. You can show what the agent changed, what the checks proved, and what still needs a human. That is a stronger position than "the agent said it was done".

A regression caught before the customer sees it lowers the cost of change, which makes the site safer to improve.

## Skills You Are Building
This develops evaluating and improving solutions, professional communication, and the judgement to decide what evidence is enough. A check is how you show your work.

# The Agent-Ready Repo and Handover 

An agent can only work with what the repository tells it. The next developer can only maintain what the repository explains. A repository that is ready for an agent is also ready for a handover.

If someone else can open the repository, run it, change it and diagnose it without asking you, the repo is ready. If they need your chat history, it is not.

## The Concept First

A repository is three things at once. It is the workspace where the build happens. It is the record of what changed and why. It is the handover pack that lets someone else take over.

Most students treat the repo as a folder for files. An agent-ready repo is a set of instructions and evidence. It tells the agent what to do before it starts. It tells the next person what happened after you leave.

The evidence files are the handover:

- `SPEC.md` says what done means.
- `DECISIONS.md` says what was chosen, why, and what was rejected.
- `CRITIQUE.md` says what is still wrong or unverified.
- `AI-USE.md` says which tools were used, for what, and what was verified.
- `README.md` says how to run and deploy the project.
- A runbook says what to do when it breaks.
- The checks say how to prove it still works.

A chat log is not a handover. It is a transcript of a conversation that the next person cannot search, trust or reproduce.

## Understanding Through a Shared Workshop

A workshop with labelled drawers, a job card, a logbook and a clean bench can be used by someone else. A workshop where everything is in one person's head cannot.

The labelled drawers are the README and the folder structure. The job card is the spec and the agent instructions. The logbook is the decision record and the commit history. The clean bench is the small diff, the removed secret and the closed branch.

A workspace that explains itself is a business asset. A workspace that only one person understands is a liability.

## The Files That Do the Work

| File | Question it answers | Who reads it |
|---|---|---|
| `AGENTS.md` | How should an agent work here? What is allowed, what is forbidden, and what proves the work is done? | The agent, and the next developer |
| `SPEC.md` | What does the client need, and what counts as done? | The client, the builder, the checker |
| `DECISIONS.md` | What did we choose, why, and what did we reject? | The next developer, the assessor, the client |
| `CRITIQUE.md` | What is still wrong or unverified? | The next developer, the client |
| `AI-USE.md` | Which tools did we use, for what, and what was verified? | The assessor, the next developer |
| `README.md` | What is this, how do I run it, and how do I deploy it? | Anyone opening the repo |
| `runbook.md` | What do I do when it breaks? | The maintainer, the IT vendor, future you |
| `checks/` and `tests/` | How do we know it still works? | The builder, the reviewer, the next developer |

Each file removes a question that would otherwise become a meeting, a message or a defect.

## AGENTS.md

`AGENTS.md` is the project instruction file for an AI agent. It lives in the repository. The agent reads it before it starts work. It is not a prompt you paste once. It is a standing contract for every session.

A useful `AGENTS.md` is short enough to read and specific enough to act on.

```markdown
# Instructions for AI agents working in this repository

## Stack

- Plain HTML, CSS and JavaScript. No frameworks, no build step.
- The site lives in `site/`.
- The provided checks live in `checks/`. Your checks live in `tests/`.

## Rules

1. Do not create, edit or delete anything in `checks/`. Fix the site, not the check.
2. Never put API keys, tokens or secrets in `site/`.
3. Make one logical change per commit, with a message that says what changed and why.
4. Do only what you are asked. Suggest other changes and wait.
5. When you say something is done, show the command and its output.
6. Read `SPEC.md` before starting. If the task conflicts with it, stop.
7. Add every new page to `pages.json`.
8. Do not add a dependency, a framework or a build step without asking.
The rules are testable. "Write clean code" is not a rule. "Do not edit `checks/`" is a rule you can check in the diff.

The agent will fill any gap with a default. If the file does not say which folder holds the site, the agent will choose one. If the file does not say which commands prove the work, the agent will claim success without evidence.

Update `AGENTS.md` after a failure. Add the rule that would have prevented it. The file should get better as the project gets harder.

## The rule that would have helped
After a bad agent change, ask one question: "What sentence in `AGENTS.md` would have stopped this?" Add it. That is a better use of five minutes than rewriting the prompt.

## Working with Your AI Partner

AI is useful at three points in this chapter. It can find the gaps in `AGENTS.md`, plan a small change with a stop condition, and review a diff for scope creep. It is a poor judge of whether the work is ready to hand over. That judgement is yours.

### Exploration 1: Find the Missing Rules

```text
Ask your AI:
Here is my AGENTS.md. List every decision you would have to guess before
you could work safely in this repo. For each guess, write the rule that
would remove it. Do not edit any files.

Add the rules that are specific and testable. Ignore generic advice such as "write clean code". A rule the agent cannot check is not a rule.

### Exploration 2: Plan Before You Act

Ask your AI:
Here is one acceptance criterion and the file it affects. Write a plan
with one change, the check that proves it, and the conditions that
should stop you. Do not write code yet.

A good plan names the file, the criterion, the check and the stop condition. If the plan is vague, the diff will be large.

### Exploration 3: Review a Diff for Scope Creep

Ask your AI:
Here is a diff. List every change that is outside the stated task. Do
not fix it. Name the scope creep and the risk it adds.

Scope creep is easier to see in a diff than in a chat. Review the diff before you review the result.

## Small Diffs

The diff is the unit of review. A large diff hides mistakes, mixes unrelated changes and makes the work impossible to explain. A small diff shows one decision at a time.

One logical change per commit. A logical change is one behaviour, one fix, one content update or one refactor. If the message needs the word "and" to describe two unrelated things, the commit is probably too large.

Ask the agent for one change at a time. Name the file, the acceptance criterion and the stop condition. Ask it to show the diff before applying it.

Ask your AI:
Change only the booking form in site/contact.html so that the party size
field has a visible label and a helpful error message. The acceptance
criterion is "The form labels every input." Do not change the layout,
the copy or any other page. Show me the diff before you apply it.

The commit message is evidence. It says what changed and why. The body can say what was rejected and which check proves the change.

| Weak message | Useful message |
|---|---|
| update | Fix 375px overflow in the menu grid |
| fix | Add a label to the party size field |
| final | Add loading and error states to the opening status widget |
| changes | Replace the hero image with the client's photo and update the alt text |

`git log --oneline` should read like a story. A reader should be able to see the build progress without opening every commit.

If the agent makes one giant commit, you can still recover. Read it with `git show`. Split it with `git add -p`, which lets you stage one hunk at a time. Or revert it and redo the work in small commits. The history is worth the effort because the history is the evidence.

### Commit Messages as Evidence

A commit message answers three questions:

1. What changed?
2. Why did it change?
3. What proves it?

Add a visible label to the party size field

The booking form used a placeholder as the only label. Screen reader
users could not tell what the field was for. The new label is visible
and connected with for/id.

Checked with npm test and a screen reader pass.

The body is not a diary. It is the reason the change exists. The next developer will read it when the code no longer makes sense.

## Plan, Act, Verify

An agent-ready workflow has three steps. They are short, and they prevent most of the mess.

Plan. Restate the task in one sentence. Name the files. Name the acceptance criterion. Name the check. Name the stop condition.

Act. Make one small change. Commit it with a message that explains the change.

Verify. Run the check. Read the diff. Open the page at 375px. Check the console. Show the evidence.

A plan sounds like this:

> The task is to make the booking action visible at 375px. The file is `site/css/styles.css`. The criterion is "The booking action is visible at 375px without scrolling." The check is `tests/booking.spec.js`. Stop if the change touches `checks/` or adds a dependency.

Name a stop condition, because the agent will keep going if you do not define the edge of the task.

### When to Stop the Agent

Stop when the agent:

- wants to change the stack;
- wants to edit `checks/`;
- wants to add a dependency or a build step;
- wants to touch secrets or environment variables;
- wants to rewrite a file wholesale;
- wants to do something outside the task;
- says it is done without showing the command and the output.

Stopping is a normal decision. Record it in `DECISIONS.md`. The agent can be wrong. You own the commit.

## Skills and Reusable Instructions

A skill is a short, reusable instruction file for a repeated task. It tells the agent how to do one job in this project.

A skill has five parts:

1. When to use it.
2. The inputs.
3. The steps.
4. The files it may touch.
5. The definition of done.

```markdown
# Skill: Add a page

## When to use

A new page is added to the site.

## Steps

1. Create `site/.html` from the shared layout.
2. Add the page to `pages.json`.
3. Add a link from the navigation.
4. Run `npm run check`.
5. Commit with a message that names the page and the criterion.

## Done when

The page is in `pages.json`, the navigation links to it, and the checks pass.
### From Workflow to Skill

The first time you do a task, you are learning it. The second time, you are checking whether the steps are stable enough to reuse. That is when you write the skill.

| Pass | Purpose | Output |
|---|---|---|
| First | Learn the workflow | A rough log of the steps, files, checks and failure points |
| Second | Confirm the steps are stable | A skill file, or a note that the task changes too much |
| Test | Prove the skill works without you | A fresh agent session and a diff you can review |

The first pass is not wasted. It is the research. Keep a rough log while you work: which files the agent touched, which check proved the change, where it went wrong, what you had to explain twice.

The first time you add a page, you might ask the agent to create `site/contact.html`. You notice that the page also needs a line in `pages.json` and a link in the navigation. The check fails if the page is missing from the list. Those are the steps that belong in the skill.

On the second pass, follow the log. If the steps are the same, write the skill. If the steps change, the task is not stable enough to codify yet. Narrow the task or keep learning.

Test the skill in a fresh session with no chat history. If the agent needs extra explanation, the skill is missing a step. Add it or narrow the task.

A skill for "add a page" is portable. A skill for "update the Northbridge menu" is project-specific. Both are useful. Keep them small.

`AGENTS.md` is the project contract. Skills are task recipes. A skill that tries to cover the whole project is an `AGENTS.md` file with a different name.

Skills make the agent more consistent. They do not make it correct. You still read the diff and run the check.

## Permissions and Secrets

The agent needs enough access to do the work and no more. That is the principle of least privilege.

- Give the agent the workspace. Do not give it the production account.
- Do not put a production key on a laptop or in a repository.
- Use environment variables and a serverless function for anything secret ().
- Keep `.env` in `.gitignore`. Commit `.env.example` with names only.
- Do not paste secrets into a prompt, a screenshot or a README.
- Read a command before you approve it. Do not approve a command you do not understand.

If a secret is committed, rotate it. Deleting the file does not remove it from history. `git log -p` can still find it. A secrets check is a teaching tool. It does not prove the repo is clean.

The same rule applies to permissions. The agent does not need admin rights, a production database or a payment account. It needs the files, the checks and a way to run them. Many managed machines have no admin rights for a reason. The browser path is the baseline, and the desktop path is an optional convenience.

## The Handover Pack

A handover pack is what you give the next person so they can run, deploy, change and diagnose the site. It is the repo made legible.

| Part | What it contains |
|---|---|
| `README.md` | What the project is, how to run it, how to deploy it, where the data lives, who to contact, known limitations |
| Runbook | Local setup, deploy steps, data sources, common failures, rollback, contacts |
| `DECISIONS.md` | Architecture choices, rejected options, costs, dates |
| `CRITIQUE.md` | Known issues, unverified areas, what to fix next |
| `AI-USE.md` | Tools, what was verified, what was rejected, where AI was not used |
| `SPEC.md` | The contract the build was judged against |
| Checks | The command that proves the site still works |
| Known issues | Severity, workaround, owner, next action |
| Contribution map | Who did what, for a team project or a handover |

The handover pack is also a business document. It reduces the cost of maintenance, the risk of a single person leaving, and the time a new developer spends asking questions.

### A Worked Handover to Alex

Alex is the IT vendor who will maintain the site after the project ends. Alex is busy, cautious and has seen too many abandoned sites. A good handover is the difference between a site that survives and a site that gets rebuilt.

A weak handover sounds like this:

> It works on my laptop. The chat has the details. The password is in the repo. Ask me if you get stuck.

A useful handover sounds like this:

> The site is in `site/`. `README.md` has the local and deploy steps. `runbook.md` covers the data sources, the common failures and the rollback. `DECISIONS.md` explains why the front end is static and why the booking form posts to a function. `CRITIQUE.md` lists the known issues, including the missing empty state on the opening status widget. `npm run check` proves the checks still pass. There are no secrets in the repo. The deploy URL and the rollback steps are in the runbook.

The second handover lets Alex run the site, deploy it, diagnose it and know what is still wrong. The first handover makes Alex open a chat and start from zero.

2. Ask for one logical change at a time.

# Structure: HTML as Information Architecture 

## The Concept First

Before we write any HTML, consider what it does: organising information so both humans and machines can understand it.

Every document you've ever read has structure. A book has chapters, sections, and paragraphs. A business report has headings, bullet points, and tables. A restaurant menu has categories, items, and descriptions. Structure is how documents communicate meaning.

HTML (HyperText Markup Language) is simply the language we use to describe document structure for the web. When you write HTML, you're not designing how something looks, you're declaring what something is.

A heading isn't big, bold text. A heading is a heading, a structural element that indicates hierarchy and importance. How it appears is a separate concern.

## Understanding Through Architecture

Think of a well-designed building:

- The foundation supports everything above it
- Walls and rooms divide space into meaningful areas
- Signs and labels tell you what each area is for
- Doors and corridors connect different spaces
- Building codes ensure safety and accessibility

Now think about a web page:

- The document declaration establishes what kind of document this is
- Semantic elements divide content into meaningful sections
- Tags label what each piece of content represents
- Links connect pages and resources
- Web standards ensure accessibility across devices

An architect doesn't just make a building that stands, they create spaces that people can navigate, understand, and use. A web developer doesn't just make a page that displays, they create documents that humans can read and machines can process.

## The Architecture Mindset
When you look at any web page, train yourself to see structure first, appearance second. Ask: "What are the meaningful sections here? How is the content organised? What is each element's purpose?"

# Presentation: CSS as Visual Communication 

## The Concept First

In , you learned to describe what content is. Now we'll control how content looks: its visual communication.

CSS (Cascading Style Sheets) determines colours, fonts, spacing, and layout. But these choices aren't arbitrary. Every visual decision communicates something: professionalism, playfulness, urgency, calm. A hospital website and a children's toy store might have identical HTML structure, but their CSS tells completely different stories.

Structure and presentation are deliberately separate. Your HTML says "this is a heading", it doesn't say "this should be blue and 24 pixels tall." CSS handles appearance. This separation means you can completely redesign a website without touching its content, or update content without breaking the design.

## Understanding Through Design

Think of two cafés with identical menus. Same coffee, same pastries, same prices.

Café A: Exposed brick, warm lighting, comfortable armchairs, handwritten chalkboard menu, soft jazz playing.

Café B: White walls, fluorescent lights, plastic chairs, printed menu in a laminated folder, no music.

The content is identical, but would you feel the same about visiting each one? The atmosphere shapes your entire perception of the business. One feels welcoming and worth paying premium prices; the other feels like a waiting room.

CSS is your website's atmosphere. The content (HTML) might be excellent, but if the presentation feels amateur, untrustworthy, or confusing, users leave.

## The Atmosphere Test
Look at any website and ask: "What is this design trying to communicate?" Before you read the words, the visual design has already told you whether this is playful or serious, cheap or premium, trustworthy or suspicious.

Classes (`.classname`) are your workhorses, reusable styles you can apply to any element. IDs (`#idname`) should be unique per page and are less commonly used in modern CSS.

### The Box Model

Every HTML element generates a rectangular box. Understanding this box model is essential for layout:

css
.card {
    padding: 20px;      / Space inside /
    border: 1px solid #ccc;
    margin: 10px;       / Space outside /

## Box-Sizing Gotcha
By default, width and height don't include padding or border. A 200px box with 20px padding becomes 240px wide. Modern practice is to add `box-sizing: border-box;` so width includes everything:

css
.container {
    display: flex;
}
This single line changes the container. Its children become "flex items" that you can arrange in rows or columns:

css
nav {
    display: flex;
    justify-content: space-between;
    align-items: center;
}
Centred content:
css
.cards {
    display: flex;
    flex-wrap: wrap;
    gap: 20px;
}
.card {
    flex: 1 1 300px;  / Grow, shrink, minimum 300px /
}
css
/ Base styles (mobile-first) /
.container {
    padding: 1rem;
}

/ Styles for screens 768px and wider /
@media (min-width: 768px) {
    .container {
        padding: 2rem;
        max-width: 800px;
        margin: 0 auto;
    }
}
Mobile-first means your base CSS is for mobile, then you add complexity for larger screens. This approach naturally prioritises essential content.

css
body {
    font-family: system-ui, -apple-system, sans-serif;
    font-size: 16px;
    line-height: 1.6;
    color: #333;
}

h1, h2, h3 {
    line-height: 1.2;
    margin-bottom: 0.5em;
}

a {
    color: #0066cc;
}

a:hover {
    color: #004499;
}
Using `rem` for sizes keeps everything relative to the base font size, making your design more adaptable:

```css
h1 { font-size: 2.5rem; }    / 40px if base is 16px /
h2 { font-size: 2rem; }      / 32px /
h3 { font-size: 1.5rem; }    / 24px /
p  { font-size: 1rem; }      / 16px /

2. Source order: Later rules override earlier ones (if specificity is equal)
3. Importance: `!important` overrides everything (but avoid using it)

# Behaviour: JavaScript as User Interaction 

## The Concept First

HTML provides structure. CSS provides presentation. JavaScript provides behaviour, the ability to respond to user actions, update content dynamically, and create interactive experiences.

Consider a contact form. HTML creates the fields and the submit button. CSS makes it look professional. But what happens when someone clicks "Submit"? What validates their input? What shows them a success message? That's JavaScript.

JavaScript makes pages respond without a reload: dropdown menus expand, forms validate as you type, and content loads in place.

But JavaScript should enhance, not replace, structure and presentation. A well-built page works without JavaScript. JavaScript makes it work better.

## Understanding Through Conversation

A static webpage is like a poster on a wall. You can look at it, but it can't respond to you.

JavaScript makes your page more like a conversation:

- It listens: "The user clicked this button"
- It thinks: "I should validate the form now"
- It responds: "Show the error message next to the email field"
- It adapts: "Now that they've fixed the email, remove the error"

This back-and-forth is called event-driven programming. Instead of running top to bottom like a recipe, JavaScript waits for things to happen (events) and responds to them.

## The Conversation Mindset
When designing interactive features, think: "What might the user do?" (events) and "How should the page respond?" (handlers). Every interaction is a small conversation between user and page.

### Form Validation Example

Here's a practical business example, validating an email field:

javascript
const form = document.querySelector('#contact-form');
const emailInput = document.querySelector('#email');
const errorSpan = document.querySelector('#email-error');

emailInput.addEventListener('input', function() {
    // Check if it looks like an email
    if (emailInput.validity.valid) {
        errorSpan.classList.add('hidden');
        errorSpan.textContent = '';
    } else {
        errorSpan.classList.remove('hidden');
        errorSpan.textContent = 'Please enter a valid email address';
    }
});

form.addEventListener('submit', function(event) {
    if (!emailInput.validity.valid) {
        event.preventDefault();  // Stop form submission
        errorSpan.classList.remove('hidden');
        errorSpan.textContent = 'Please enter a valid email address';
    }
});

This validates as the user types and again on submission. Note: HTML5 provides `type="email"` validation too. JavaScript improves the feedback on top of that baseline.

# Connection: APIs as Business Integration 

## The Concept First

So far, everything you've built lives in isolation. Your HTML, CSS, and JavaScript create an experience, but that experience is self-contained, it doesn't connect to anything beyond itself.

Real business applications are different. They display live weather data. They process payments. They show inventory levels. They sync with customer databases. They pull content from external services.

They do it through APIs (Application Programming Interfaces).

An API is a defined way for two systems to communicate. When your JavaScript asks a weather service "What's the temperature in Perth?", it's using an API. When a customer's payment details go to Stripe for processing, that's an API. When your portfolio site pulls your latest GitHub projects, that's an API.

APIs connect your website to those services instead of leaving it standalone.

## Understanding Through Contracts

Think of an API as a contract between two parties. Like any good contract, it specifies:

- What you can ask for (the endpoints)
- How to ask (the request format)
- What you'll receive (the response format)
- What happens if something goes wrong (error handling)

Imagine a restaurant:

- The menu lists what you can order (available endpoints)
- You place an order in a specific way, verbally to a waiter, on a printed slip (request format)
- The kitchen prepares your food and the waiter delivers it (response)
- If something's unavailable, they tell you (error response)

You don't need to know how the kitchen works. You just need to know how to order and what to expect.

## The Contract Mindset
When working with any API, first understand the contract: What can I request? What format does it expect? What will I receive? What errors might occur? Read the documentation before writing code.

### The Fetch API

JavaScript's `fetch()` function makes HTTP requests:

```javascript
fetch('https://api.example.com/products')
    .then(response => response.json())
    .then(data => {
        console.log(data);
    });
This fetches data from a URL, converts the response to JSON, and logs it. But what's with all those `.then()` calls?

### Understanding Asynchronous Code

API requests take time. The server might be across the world. Your code can't just wait, it would freeze the entire page.

JavaScript handles this with asynchronous code. Instead of stopping and waiting, it says "start this request, and when it's done, run this code."

The `.then()` pattern is called a Promise. But modern JavaScript has a cleaner syntax: `async`/`await`.

### Async/Await: Readable Asynchronous Code

```javascript
async function loadProducts() {
    const response = await fetch('https://api.example.com/products');
    const data = await response.json();
    console.log(data);
}

loadProducts();

`await` pauses the function (not the whole page) until the operation completes. The `async` keyword marks functions that use `await`.

This reads more naturally: "Fetch the URL. Wait. Parse the JSON. Wait. Log the data."

### A Complete Example: Displaying API Data

Let's fetch real data and display it:

javascript
async function displayProducts() {
    const container = document.querySelector('#product-list');

    try {
        const response = await fetch('https://fakestoreapi.com/products?limit=3');
        const products = await response.json();

        // Clear loading message
        container.innerHTML = '';

        // Create HTML for each product
        products.forEach(product => {
            const productCard = document.createElement('div');
            productCard.classList.add('product-card');
            productCard.innerHTML = `
                ${product.title}
                $${product.price}
            `;
            container.appendChild(productCard);
        });

    } catch (error) {
        container.innerHTML = 'Sorry, products could not be loaded.';
        console.error('Fetch failed:', error);
    }
}

displayProducts();

Key elements:

1. Show a loading state initially
2. Fetch data with `await`
3. Parse JSON with `await`
4. Create DOM elements for each item
5. Handle errors with `try`/`catch`

async function loadData() {
    try {
        const response = await fetch('https://api.example.com/data');

        // Check if the response was successful
        if (!response.ok) {
            throw new Error(`HTTP error: ${response.status}`);
        }

        const data = await response.json();
        return data;

    } catch (error) {
        if (error.name === 'TypeError') {
            // Network failure - couldn't reach the server
            console.error('Network error:', error);
            return { error: 'Unable to connect. Please check your internet.' };
        } else {
            // Other error (including our HTTP error)
            console.error('Fetch error:', error);
            return { error: 'Something went wrong. Please try again.' };
        }
    }
}

## Check `response.ok`
A `fetch()` that reaches the server won't throw an error even if the server returns a 404 or 500 status. You must check `response.ok` to detect these failures.

### Loading States

Users should never see a blank screen while waiting:

```javascript
async function loadWithStatus() {
    const container = document.querySelector('#content');
    const loadingMessage = document.querySelector('#loading');

    // Show loading state
    loadingMessage.classList.remove('hidden');
    container.innerHTML = '';

    try {
        const response = await fetch('https://api.example.com/data');
        if (!response.ok) throw new Error('Fetch failed');

        const data = await response.json();
        displayData(data, container);

    } catch (error) {
        container.innerHTML = 'Unable to load content.';

    } finally {
        // Always hide loading, whether success or failure
        loadingMessage.classList.add('hidden');
    }
}
The `finally` block runs regardless of success or failure, perfect for cleanup like hiding loading spinners.

### HTTP Methods: Beyond GET

So far we've used GET (fetching data). Other methods exist:

```javascript
// POST - create new data
const response = await fetch('https://api.example.com/orders', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json'
    },
    body: JSON.stringify({
        product: 'Coffee',
        quantity: 2
    })
});

// PUT - replace existing data
await fetch('https://api.example.com/orders/123', {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ product: 'Tea', quantity: 3 })
});

// DELETE - remove data
await fetch('https://api.example.com/orders/123', {
    method: 'DELETE'
});

| Method | Purpose | Has Body? |
|--------|---------|-----------|
| GET | Read data | No |
| POST | Create new data | Yes |
| PUT | Replace data completely | Yes |
| PATCH | Update part of data | Yes |
| DELETE | Remove data | Usually no |

### CORS: Why Some Requests Fail

You might encounter this error:

> Access to fetch at 'https://other-site.com/api' has been blocked by CORS policy

CORS (Cross-Origin Resource Sharing) is a security feature. By default, JavaScript can only fetch from the same domain the page is on. To fetch from a different domain, that domain must explicitly allow it.

Ask your AI:
Explain CORS in simple terms. Why does it exist? What's it protecting
against?

As a frontend developer, you can't fix CORS on a third-party server. Your options:

1. Use APIs that allow CORS (most public APIs do)
2. Ask the API provider to enable CORS
3. Use a backend proxy (your server fetches the data)

## Building Your Mental Model

### Request-Response Cycle

Every API interaction follows this pattern:

┌──────────────┐     Request      ┌──────────────┐
│              │ ──────────────▶  │              │
│   Browser    │                  │    Server    │
│  (Your JS)   │ ◀──────────────  │    (API)     │
│              │     Response     │              │
└──────────────┘                  └──────────────┘

1. Your JavaScript builds a request (URL, method, body, headers)
2. Browser sends it across the network
3. Server processes and responds
4. Your JavaScript handles the response

Everything that can go wrong, network issues, server errors, malformed data, happens in this cycle.

### Synchronous vs Asynchronous

Synchronous (blocking):
Step 1 → Wait → Step 2 → Wait → Step 3

Asynchronous (non-blocking):
Step 1 → Start Step 2 (don't wait) → Step 3
                ↓
         Step 2 completes → Handle result

`async`/`await` makes asynchronous code look synchronous while keeping the page responsive.

### The Data Flow

API Response (JSON string)
        ↓
   response.json() (parse)
        ↓
JavaScript Objects/Arrays
        ↓
   Process & Transform
        ↓
   Create DOM Elements
        ↓
   Page Updates

Understanding this flow helps debug issues: Is the problem in fetching? Parsing? Processing? Rendering?

- Accounting software

# Why CMS? The Business Value of Managed Content 

## The Concept First

In the Web Foundations chapters, you built websites by writing code. Every heading, every paragraph, every image, you placed them precisely where they belonged. You had complete control.

Most business websites need regular content updates, and most content updates shouldn't require a developer.

Consider a small business website. The owner wants to:

- Add a new service offering next week
- Update prices when costs change
- Post news about an upcoming event
- Change the phone number when they move offices

If every change requires editing HTML files and redeploying, that business has a problem. They either pay a developer for simple updates or let their site become stale.

A Content Management System (CMS) solves this by separating content from code. The developer builds the structure and design once. Then, the business owner, without touching code, can create, edit, and publish content through a friendly interface.

That makes a CMS a business architecture decision, one that affects costs, maintenance, and who controls what.

## Understanding Through Roles

Think about how a newspaper works:

- Journalists write articles. They focus on content quality, not page layout.
- Editors review and approve content before publication.
- Designers create the newspaper's visual templates and structure.
- Printers produce the physical paper at scale.

Each role has its own expertise and focuses on its domain. The journalist doesn't need to understand printing presses; they need a system that accepts their article and handles everything else.

A CMS creates similar role separation for websites:

- Content creators write and manage content through an interface
- Administrators control permissions, workflows, and settings
- Developers build themes, extend functionality, and handle technical concerns
- Visitors see the published result

Content creators never see code. Developers rarely touch content. Each role works in their comfort zone, and the system coordinates.

## The Handoff Test
A website is truly "done" when you can hand it to the client and they can manage their own content. If they need to call a developer for every text change, the project succeeded technically but failed practically.

## Discovering CMS Concepts with Your AI Partner

## From Concept to Code (Understanding CMS Architecture)

While this chapter focuses on concepts, let's understand what a CMS does technically.

### The Core Separation

Without a CMS:
HTML File → Browser
(Content is embedded in code)

With a CMS:
Database (Content) + Templates (Design) → CMS Engine → HTML → Browser
(Content and presentation are separate)

The CMS combines content from a database with design templates to generate the HTML that browsers display. Change the content in the database, and the generated HTML changes, without touching any code.

### CMS Types

Not all CMSs work the same way:

Traditional CMS (Coupled)

- Content management and website delivery are one system
- Examples: WordPress, Drupal, Joomla
- Good for: Standard websites, blogs, small-medium businesses
- The CMS generates and serves the web pages

Headless CMS (Decoupled)

- Content management is separate from content delivery
- Content is accessed via API, displayed by a separate frontend
- Examples: Contentful, Strapi, Sanity
- Good for: Multi-channel content (web, mobile, kiosk), developer-led projects
- We'll explore this in 

Website Builders (All-in-one)

- Simplified CMS with built-in design tools
- Examples: Squarespace, Wix, Webflow
- Good for: Simple sites, non-technical users, quick launches
- Limited flexibility but minimal technical requirement

### WordPress: The Dominant CMS

WordPress powers over 40% of all websites: nearly half of the web runs on this one platform.

Why? Because it hits a sweet spot:

- Free and open source: No licensing costs
- Massive ecosystem: Thousands of themes and plugins
- Flexible: Blogs, business sites, e-commerce, anything
- Accessible: Non-developers can manage content
- Extensible: Developers can customise deeply

We'll spend the WordPress chapters learning to use WordPress properly, evaluate it professionally, and extend it when needed.

### The CMS Decision Framework

When evaluating whether a project needs a CMS:

| Factor | Suggests CMS | Suggests Custom Code |
|--------|-------------|---------------------|
| Content updates | Frequent (weekly+) | Rare (yearly) |
| Content editors | Non-technical staff | Developers only |
| Content volume | Growing over time | Fixed/static |
| Budget for updates | Limited ongoing budget | Developer always available |
| Time to launch | Faster with templates | Longer but fully custom |
| Unique requirements | Standard patterns work | Highly unusual needs |

hours. They update the menu monthly. The owner isn't technical.

and what type might be appropriate.

## Building Your Mental Model

### Content as Structured Data

In a CMS, content is structured data with defined fields:

Blog Post:
├── Title (text, required)
├── Content (rich text)
├── Author (relationship to User)
├── Category (relationship to Category)
├── Featured Image (media)
├── Publish Date (date)
└── Status (draft/published)

This structure enables:

- Consistent presentation (every post has the same fields)
- Searchability (find all posts by author)
- Relationships (posts belong to categories)
- Validation (required fields must be filled)

Ask your AI:
For a small business website with services, team members, and
testimonials, what content types would I need? What fields would
each content type have?

### The Template Layer

Templates define how structured content becomes visual HTML:

Template: "Single Blog Post"
┌────────────────────────────────────┐
│  {{ post.featured_image }}          │
│  {{ post.title }}          │
│  By {{ post.author.name }}   │
│  {{ post.content }}                 │
└────────────────────────────────────┘

The template pulls fields from the content and arranges them. Change the template, and every post's appearance changes. Change one post's content, and only that post changes.

This separation lets designers work on templates while writers work on content, and neither needs to understand the other's domain.

### The Permission Layer

CMSs control who can do what:

- Administrator: Full access to everything
- Editor: Can manage all content but not settings
- Author: Can write and publish their own content
- Contributor: Can write but not publish (needs approval)

These roles prevent accidents ("The intern deleted the homepage") and enable workflows ("All posts need editor approval before publishing").

## Business Applications

### Client Handoff

A website project succeeds when the client can maintain the site independently after launch. A CMS-based site can be handed off with training:

"Here's how you add a new blog post. Here's how you update your hours. Here's how you add a team member."

Custom-coded sites often create ongoing dependency.

### Reduced Maintenance Costs

Every developer-required change has a cost. With a CMS:

- Content changes: Client handles directly ($0)
- Design tweaks: Occasional developer work
- Major features: Developer project

Without a CMS:

- Content changes: Developer required ($$$)
- Everything requires technical involvement

Over years, this difference compounds.

2. Content team adds 50 products through the interface
3. Products appear on the site automatically

Without a CMS: a developer writes and deploys 50 pages of HTML.

# WordPress as Platform 

## The Concept First

WordPress powers over 40% of the web: nearly half of all websites run on a single platform. Understanding why reveals something important about how technology decisions are made in business.

Treat WordPress as a platform, a foundation that others build upon:

- Software does specific things. You use it as-is.
- A platform provides a foundation. An ecosystem builds on top of it.

Your smartphone is a platform. The core provides basics (calls, settings), but the app ecosystem gives it most of its capability. You don't judge your phone by its built-in apps alone, you judge it by what you can do with the apps others have built.

WordPress works the same way. The core handles content management. Themes control appearance. Plugins add functionality. The ecosystem, over 60,000 plugins, thousands of themes, is what makes WordPress suitable for almost any website.

Learning WordPress means learning to evaluate and assemble these pieces professionally.

## Understanding Through Ecosystems

Imagine opening a restaurant. You could:

Option A: Build everything from scratch. Design your own stoves, create your own recipes, invent your own point-of-sale system.

Option B: Use standard commercial kitchen equipment, adapt proven recipes, install established POS software, then focus your creativity on your unique menu and dining experience.

Option B gets you open faster, with tested components, and lets you focus on what makes your restaurant special.

WordPress provides the kitchen equipment. Themes provide the interior design. Plugins provide specialised tools (reservation systems, online ordering). You focus on your content and business logic.

## The Platform Evaluation Question
When evaluating any platform, ask: "How active is the ecosystem?" A platform with a dying ecosystem becomes a liability. WordPress's ecosystem is massive and active, a significant factor in its dominance.

### The Template Hierarchy

WordPress uses a template hierarchy to determine which template file displays content. Understanding this helps when you need to customise.

Specific                                      General
───────────────────────────────────────────────────────►

Single Post:
single-post-{slug}.php → single-post.php → single.php → singular.php → index.php

Single Page:
page-{slug}.php → page-{id}.php → page.php → singular.php → index.php

Archive:
category-{slug}.php → category.php → archive.php → index.php

WordPress looks for the most specific template first, falling back to more general ones. This allows themes to have special templates for specific pages while using defaults for everything else.

### Content Separation

A useful mental model: content lives in the database, presentation lives in the theme.

Database (content):
├── Post: "Our Spring Menu"
│   ├── Title
│   ├── Body content
│   ├── Featured image reference
│   └── Categories, tags

Theme (presentation):
├── How to display a post
│   ├── Where title appears
│   ├── Image placement
│   └── Typography, colours

This separation is why you can change themes without losing content.

### The Hook System

WordPress allows code to "hook" into specific points in the execution flow. While you won't write hooks yet, understanding they exist explains how plugins modify WordPress without changing core files:

- Plugins register functions to run at specific points
- WordPress calls these functions when reaching those points
- Multiple plugins can hook into the same point

This architecture is why WordPress is extensible without modification, a defining platform characteristic.

# Extending Platforms 

## The Concept First

In , you learned that WordPress's value lies in its ecosystem. Now we'll learn to extend WordPress professionally, using plugins wisely, customising safely, and making business decisions about when to build versus when to buy.

Plugins make WordPress more capable, but they also create risk. Every plugin you add:

- Depends on someone else maintaining it
- Could conflict with other plugins
- Might introduce security vulnerabilities
- Adds complexity to troubleshoot

Professional WordPress development means installing the right plugins and knowing when custom development makes more sense.

## Understanding Through Build vs Buy

Every feature request presents a choice:

Buy (Use existing plugin):

- Faster to implement
- Someone else maintains it
- Tested by thousands of users
- May not fit exact requirements

Build (Custom development):

- Exact fit for requirements
- You control maintenance
- No dependency on external developers
- Higher upfront cost

Neither is always better. The professional skill is evaluating trade-offs.

Consider a business that needs a booking system:

| Factor | Plugin (e.g., Bookly) | Custom Build |
|--------|----------------------|--------------|
| Implementation time | Hours | Weeks |
| Upfront cost | $0-300 | $5,000-20,000 |
| Fits requirements | 80-90% | 100% |
| Ongoing updates | Plugin developer | You |
| Customisation | Limited | Unlimited |
| Risk of abandonment | Medium | None (you own it) |

For most small businesses, the plugin wins. For a booking-centric business with unique requirements, custom might justify its cost.

## The 80% Rule
If an existing solution meets 80% of requirements, adapting workflows to fit the tool often costs less than building the remaining 20% custom. Perfect fit isn't always worth the price.

### Plugin Conflicts

Plugins can conflict because they:

- Modify the same functionality
- Use incompatible JavaScript libraries
- Compete for database resources
- Override the same hooks

Diagnosing conflicts:

1. Note the symptoms (error messages, broken features)
2. Deactivate all plugins
3. Reactivate one by one, testing each time
4. Identify the conflicting combination
5. Decide: replace one, find alternative, or contact support

Preventing conflicts:

- Minimise plugin count (each one adds risk)
- Choose well-maintained plugins
- Test updates on staging first
- Keep WordPress core updated

### When to Build Custom

Consider custom development when:

- No plugin meets the core requirement
- Plugins would require heavy modification anyway
- The feature is central to the business model
- Security or performance requirements are extreme
- Long-term cost of plugin licensing exceeds development

- A small custom plugin (focused, maintainable)
- Modifying an existing plugin (with a child plugin approach)
- Combining simpler plugins with custom glue code

Full custom rarely means starting from zero.

### The Dependency Chain

Every plugin creates a dependency:

Your Site
  └── Depends on Plugin A
        └── Depends on Plugin A's Developer
              └── Depends on Developer's continued interest
                    └── Depends on WordPress compatibility

More plugins = more dependencies = more things that can break.

### The True Cost Formula

When evaluating options:

True Cost = Upfront Cost + (Yearly Maintenance × Years) + Risk Cost

Plugin:
- Upfront: $0-300 (purchase/license)
- Maintenance: $50-100/year (updates, support subscription)
- Risk: plugin abandonment, security issues

Custom:
- Upfront: $5,000-20,000 (development)
- Maintenance: $500-2,000/year (updates, hosting, developer retainer)
- Risk: developer availability, scope creep

Over 5 years, the math often favours plugins for standard features.

## Business Applications

### ROI Calculation

Present plugin decisions to clients in business terms:

"A custom booking system would cost $15,000 to build and $2,000/year to maintain. The plugin costs $200/year. Over 5 years:

- Custom: $15,000 + ($2,000 × 5) = $25,000
- Plugin: $200 × 5 = $1,000

The plugin doesn't do everything you want, but is that extra functionality worth $24,000?"

# Headless Architecture 

## The Concept First

In previous chapters, WordPress handled everything: it stored content, managed users, and generated the HTML visitors see. The content management and the website delivery were one unified system.

Headless architecture separates these concerns. WordPress becomes a content backend, storing and managing content, while a separate frontend application handles presentation. They communicate through APIs.

Why would you do this? Because sometimes you want:

- WordPress's excellent content management
- A modern frontend built with React or other frameworks
- Content delivered to multiple channels (web, mobile apps, kiosks)
- The performance benefits of static or cached frontends
- Complete design freedom unconstrained by WordPress themes

This approach is increasingly common for larger projects, media companies, and organisations with sophisticated frontend needs.

## Understanding Through Separation

Imagine a restaurant operation:

Traditional restaurant (traditional WordPress):

- Kitchen and dining room in one building
- Chefs prepare food, servers deliver it directly
- Simple, everything coordinated, but limited to that one location

Central kitchen + multiple outlets (headless):

- Central kitchen prepares food (WordPress manages content)
- Multiple dining locations serve customers (web, mobile, etc.)
- Food travels via delivery (API)
- Each outlet can have different ambiance (different frontends)
- Kitchen changes don't require redesigning dining rooms

The central kitchen can supply a fine dining restaurant, a casual café, and a food truck, each with completely different presentations of the same underlying food.

## Headless = API-First
"Headless" means the CMS has no "head", no built-in frontend. It's all backend. Content exits only through APIs, and something else (the "head") must display it.

### The WordPress REST API

WordPress includes a built-in REST API. Every WordPress site (version 4.7+) automatically exposes content through standardised endpoints.

Default endpoints:

| Endpoint | Returns |
|----------|---------|
| `/wp-json/wp/v2/posts` | Blog posts |
| `/wp-json/wp/v2/pages` | Pages |
| `/wp-json/wp/v2/categories` | Categories |
| `/wp-json/wp/v2/tags` | Tags |
| `/wp-json/wp/v2/media` | Media items |
| `/wp-json/wp/v2/users` | Users (public info) |

Try it yourself: If your local WordPress site is running, visit `http://your-site.local/wp-json/wp/v2/posts` in your browser. You'll see JSON data for your posts.

### Filtering and Pagination

The API supports query parameters:

```javascript

| Parameter | Purpose | Example |

| `orderby` | Sort field | `?orderby=title` |

### When Headless Makes Sense

| Scenario | Why Headless? |
|----------|---------------|
| Multi-channel delivery | Same content to web, iOS app, Android app, smart displays |
| Maximum performance | Static site generation, edge caching |
| Complex frontend needs | Single-page applications, heavy JavaScript interactivity |
| Developer preferences | Modern frontend frameworks, component architecture |
| Integration requirements | Content feeds into existing applications |

### When Traditional Makes Sense

| Scenario | Why Traditional? |
|----------|------------------|
| Content editors need preview | See exactly what's published |
| Simple sites | Blog, brochure site, small business |
| Limited technical resources | No frontend developers available |
| Plugin-dependent features | Many plugins expect traditional setup |
| Budget constraints | Two systems cost more to maintain |

### The Complexity Cost

Headless adds complexity:

- Two codebases instead of one
- Two deployments to manage
- Content preview is harder
- Some WordPress plugins don't work
- More technical expertise required

This complexity has costs, so use headless when the benefits outweigh them.

## Business Applications

### Multi-Channel Content

Organisations increasingly need content everywhere:

- Corporate website
- Mobile applications
- Internal dashboards
- Digital signage
- Partner integrations

With headless, content is created once and consumed everywhere. WordPress becomes the "single source of truth."

### Performance and SEO

Headless frontends can be:

- Statically generated (fastest possible)
- Cached at the edge (CDN)
- Optimised specifically for performance

This matters for SEO and user experience. Google measures page speed.

### Security Benefits

In headless architecture:

- WordPress can be hidden from the public (private network)
- Attack surface is reduced
- Frontend has no direct database access
- Compromising the frontend doesn't compromise content

For high-security needs, this separation is valuable.

### Developer Experience

Modern frontend developers often prefer:

- React, Vue, or similar frameworks
- Component-based architecture
- TypeScript
- Modern build tools

Headless lets them use their preferred tools while using WordPress's content management.

# Component Thinking: React 

## The Concept First

In , you learned to fetch content from WordPress via API. But vanilla JavaScript DOM manipulation becomes unwieldy as applications grow. Every change requires finding elements, updating them, keeping track of what's displayed.

React solves this by introducing a different mental model: component thinking.

Instead of thinking "I need to update this paragraph when data changes," you think "This component displays data. When data changes, React handles the update."

Components are self-contained pieces of UI. Each component:

- Has its own logic
- Manages its own state (data that changes)
- Renders its own output
- Can be reused anywhere

That changes how you build interfaces. Once you think in components, you'll see every UI as a composition of reusable pieces.

## Understanding Through LEGO

Consider how LEGO works:

- Each brick is self-contained with a consistent interface (the studs)
- Complex structures emerge from combining simple pieces
- The same brick can be used in many different creations
- You can replace one brick without rebuilding everything
- Instructions show composition, not monolithic assembly

React components work the same way:

- Each component is self-contained with consistent interfaces (props)
- Complex UIs emerge from combining simple components
- The same component can be reused throughout your application
- You can update one component without touching others
- Your code shows composition: components containing components

Treat a webpage as a tree of components, each responsible for its own piece of the interface.

## The Decomposition Instinct
When you see any interface, practice breaking it into components. A navigation bar? That's a `Nav` component containing `NavLink` components. A product card? That's a `ProductCard` containing `Image`, `Title`, `Price`, and `Button` components. This instinct transfers to any component framework.

### Exploration 2: State vs Props

React has two ways data lives in components: state (data the component owns and can change) and props (data passed from a parent).

Ask your AI:

A common analogy:

- Props are like instructions parents give to children: "Here's your allowance amount, here's your bedtime." The child receives them but doesn't change them.
- State is like the child's own possessions: "I have $5 saved, I'm currently awake." The child controls these and they can change.

### Exploration 3: Data Flow

Data in React flows one direction: parent to child (downward).

Ask your AI:

to data flowing any direction?

One-way data flow means:

- You always know where data came from
- Debugging is simpler (trace upward to find the source)
- Components are predictable
- Changes don't cause cascading side effects

### useEffect: Side Effects and Data Fetching

Components sometimes need to do things besides rendering: fetch data, set up subscriptions, update the document title. These are side effects.

```jsx
import { useState, useEffect } from 'react';

function PostList() {
    const [posts, setPosts] = useState([]);
    const [loading, setLoading] = useState(true);
    const [error, setError] = useState(null);

    useEffect(() => {
        async function fetchPosts() {
            try {
                const response = await fetch(
                    'https://jsonplaceholder.typicode.com/posts?_limit=5'
                );
                if (!response.ok) throw new Error('Failed to fetch');
                const data = await response.json();
                setPosts(data);
            } catch (err) {
                setError(err.message);
            } finally {
                setLoading(false);
            }
        }

        fetchPosts();
    }, []); // Empty array means "run once on mount"

    if (loading) return Loading...;
    if (error) return Error: {error};

    return (
        
            {posts.map(post => (
                {post.title}
            ))}
        
    );
}

The `useEffect` hook:

- Runs after the component renders
- The empty `[]` dependency array means "run only once"
- Perfect for data fetching when component loads

## Building Your Mental Model

### The Component Tree

Your application forms a tree of components:

App
├── Header
│   ├── Logo
│   └── Navigation
│       └── NavLink (×3)
├── Main
│   ├── Sidebar
│   └── PostList
│       └── PostCard (×n)
└── Footer

Data flows down this tree. State lives in the component that "owns" it, often a parent that passes it to children.

### When State Should "Lift Up"

If two sibling components need the same data, the state should live in their common parent:

Before (broken):                After (working):
ProductFilter (has state)       ProductPage (has state)
ProductList (needs state)       ├── ProductFilter (receives props)
(How does List get Filter's     └── ProductList (receives props)
 state? They're siblings!)

This is called "lifting state up", moving state to the lowest common ancestor.

### The Rendering Cycle

State Changes
     ↓
React Re-renders Component
     ↓
New JSX Generated
     ↓
React Compares to Previous
     ↓
Only Changed Parts Update in DOM

You don't touch the DOM. You declare what should appear based on state. React efficiently updates only what changed.

## Business Applications

### Reusability

Build a `Button` component once with variants (primary, secondary, danger). Use it everywhere. Update the design in one place, and every button updates.

### Team Collaboration

### Testing

Components can be tested in isolation. Does `ProductCard` render correctly with these props? Does `Counter` increment when clicked? Unit tests are straightforward.

### Design Systems

React components naturally form design systems. Your `Button`, `Card`, `Input`, and `Modal` components become a library that enforces consistency across the application.

# Rapid Development: CSS Frameworks 

## The Concept First

In , you learned CSS from scratch, selectors, box model, flexbox, media queries. But building every project from zero is slow, and consistency across large applications is hard.

CSS frameworks solve this by providing pre-built styles, components, and design decisions. Instead of designing every button, input, and card yourself, you adopt tested patterns that work together.

Using a framework is leverage. Professional developers use frameworks to move faster while maintaining quality. The skill is knowing when to use them, which to choose, and how to customise them for specific needs.

## Understanding Through Design Systems

Large organisations don't let every designer create their own button styles. They create design systems, documented collections of components, colours, typography, and patterns that ensure consistency.

Google has Material Design. Apple has Human Interface Guidelines. Salesforce has Lightning Design System. These define how interfaces should look and behave across products.

CSS frameworks are design systems you can adopt immediately:

- Bootstrap: Component-focused system with pre-built UI elements
- Tailwind CSS: Utility-focused system with building blocks for custom designs
- Foundation, Bulma, Chakra UI: Other popular options

Each makes different trade-offs. Understanding those trade-offs is how you choose between them.

## Constraints Enable Speed
Paradoxically, constraints often speed up creative work. When you don't have to decide every colour, spacing, and font size, you can focus on structure and user experience. Frameworks provide productive constraints.

# Professional Practices 

## The Concept First

In , you learned to build interfaces quickly with CSS frameworks. But professional development is about building systems that keep working and that a team can maintain.

Consider the difference:

- Hobbyist: Gets the feature working, moves on
- Professional: Gets the feature working, ensures it stays working, makes it easy for others to understand and modify

Professional practices are risk management. Every project eventually faces:

- "It was working yesterday. What changed?"
- "I can't remember why I wrote this code."
- "Someone else needs to fix this while I'm on holiday."
- "The client changed their mind. Can we undo this?"

Professional practices answer these questions before they become crises, so code keeps working tomorrow as well as today.

## Understanding Through Craftsmanship

Consider two furniture makers:

The first measures wood, cuts it, assembles pieces. If something doesn't fit, they shave a bit here, add a shim there. The table works, but any later modification requires figuring out all the adjustments again.

The second measures twice, documents the cuts, keeps offcuts labelled, photographs each stage. If something doesn't fit, they can trace exactly where the deviation started. Years later, they can build a matching chair.

Both produce functional furniture. But the second can:

- Train apprentices using their documentation
- Reproduce work reliably
- Fix problems systematically
- Collaborate with other craftspeople

Software development is the same. Version control is measuring twice. Testing is quality checks before delivery. Documentation is the labelled workshop.

## Professional Practice Serves Future You
In six months, you won't remember why you made certain decisions. Professional practices create a trail for "future you" to follow. That's not extra work, it's insurance.

## From Concept to Code

### Git: Version Control Fundamentals

Git tracks changes to files over time. The mental model:

Working Directory → Staging Area → Repository
    (your files)     (ready to commit)  (permanent history)

Initial setup:

bash
# Create a new repository
git init

# Or clone an existing one
git clone https://github.com/username/repo.git

Basic workflow:

```bash
# See what's changed
git status

# Stage changes (prepare to commit)
git add filename.js
git add .  # Stage all changes

# Commit (save to history)
git commit -m "Add user login feature"

# View history
git log --oneline
Understanding the commands:

| Command | What it does |
|---------|-------------|
| `git status` | Shows changed, staged, and untracked files |
| `git add` | Moves changes to staging area |
| `git commit` | Creates permanent snapshot with message |
| `git log` | Shows commit history |
| `git diff` | Shows what changed (unstaged changes) |

## Commit Messages Matter
Good: "Fix login timeout on slow connections"
Bad: "Fixed bug" or "Updates"

The message should explain why you made the change, not what files you touched. Future you needs to understand the intent.

# Evaluating Emerging Technologies 

## The Concept First

In , you learned practices that make developers effective. But technologies change constantly. The frameworks popular today may be legacy tomorrow. The "best practices" of five years ago may now be anti-patterns.

This creates a challenge: how do you evaluate new technologies without getting swept up in hype?

You cannot know every new tool. Instead, develop a systematic evaluation framework that works for any technology.

Consider the difference:

- Chasing trends: "Everyone's using X, we should too"
- Systematic evaluation: "X solves problem Y with trade-offs Z. Given our context, is it appropriate?"

The second approach serves you for your entire career, regardless of which technologies rise and fall.

## Understanding Through Investment Thinking

Adopting a technology is an investment decision. Like financial investments, technology investments have:

- Upfront costs: Learning time, integration effort, migration pain
- Ongoing costs: Maintenance, updates, ecosystem changes
- Expected returns: Productivity gains, capability improvements, competitive advantages
- Risks: Technology abandonment, breaking changes, hiring difficulties

Smart investors don't just ask "Will this stock go up?" They ask "Given my goals, timeline, and risk tolerance, is this the right investment?"

Smart technologists don't just ask "Is this technology good?" They ask "Given our problem, team, timeline, and constraints, is this technology appropriate?"

## The Hype Cycle Awareness
New technologies typically follow a pattern: initial hype, peak of inflated expectations, trough of disillusionment, and finally a plateau of productivity. Understanding where a technology sits on this curve helps calibrate your evaluation.

## Discovering Evaluation with Your AI Partner

### Exploration 1: Building an Evaluation Framework

Ask your AI:
Help me create a comprehensive framework for evaluating whether a
business should adopt a new web technology. What categories of
questions should I ask? Walk me through the thinking process.

A good framework might include:

Problem Fit:
- What specific problem does this solve?
- Do we actually have this problem?
- How are we solving it currently?
- How painful is the current solution?

Maturity and Stability:
- How long has this technology existed?
- Who is using it in production?
- How frequently do breaking changes occur?
- What's the governance model (company, community, foundation)?

Ecosystem and Support:
- What's the documentation quality?
- How active is the community?
- Are there quality learning resources?
- Can we hire people who know this?

Integration and Migration:
- How does this fit with our existing stack?
- What's the migration path?
- Can we adopt incrementally?
- What's the rollback strategy?

Total Cost:
- What's the learning curve?
- What are ongoing maintenance requirements?
- Are there licensing costs?
- What's the opportunity cost of adoption time?

Continue the conversation:
Now apply this framework to evaluate whether a small business
should adopt TypeScript for their JavaScript projects. Walk me
through each category.

### Exploration 2: Distinguishing Hype from Value

This should reveal patterns:

Signs of hype without substance:
- Solves problems most projects don't have
- Benefits are vague ("makes development better")
- Requires rewriting everything to adopt
- Community focuses on features, not outcomes

Signs of genuine value:
- Addresses real, common pain points
- Benefits are concrete and measurable
- Can be adopted incrementally
- Users talk about problems solved, not features

## From Concept to Code

### TypeScript: Adding Types to JavaScript

TypeScript adds static typing to JavaScript. The evaluation:

Problem it solves:
- Runtime errors from type mismatches
- Difficulty understanding code at scale
- Refactoring without confidence
- Poor IDE support for large codebases

Trade-offs:
- Additional compilation step
- Learning curve for type system
- More verbose code
- Build tooling complexity

Example comparison:

typescript
// TypeScript
function calculateDiscount(price: number, percentage: number): number {
    return price * (percentage / 100);
}

// Errors caught at compile time
calculateDiscount("100", "10");  // Error: Argument of type 'string' is not assignable
calculateDiscount(100);          // Error: Expected 2 arguments, but got 1

When TypeScript makes sense:
- Teams larger than 2-3 people
- Codebases expected to grow significantly
- APIs consumed by multiple clients
- Long-lived projects

When to skip TypeScript:
- Quick prototypes
- Solo projects with short lifespans
- Teams with no TypeScript experience and tight deadlines

Ask your AI:
I'm starting a new React project. It's a dashboard for internal use
by about 50 employees, built by me and one other developer, expected
to be maintained for 3-5 years. Should we use TypeScript? Walk me
through the decision.

### Progressive Web Apps (PWAs)

PWAs use web technologies to deliver app-like experiences.

Problem they solve:
- App store friction for distribution
- Need for offline functionality
- Push notification capability
- Installation on home screen

Trade-offs:
- More complex than standard websites
- iOS support limitations
- Not all native features available
- User education about "installation"

Basic PWA structure:

json
// manifest.json
{
    "name": "My Application",
    "short_name": "MyApp",
    "start_url": "/",
    "display": "standalone",
    "background_color": "#ffffff",
    "theme_color": "#3498db",
    "icons": [
        {
            "src": "/icon-192.png",
            "sizes": "192x192",
            "type": "image/png"
        }
    ]
}

When PWAs make sense:
- Content-focused apps needing offline access
- Avoiding app store distribution
- Cross-platform with single codebase
- Re-engagement via notifications

When to use native/hybrid instead:
- Heavy device feature requirements
- Performance-critical applications
- App store presence is valuable
- Complex offline data sync needs

### Server Components and SSR

Modern frameworks offer server-side rendering and server components.

Problem they solve:
- Slow initial page load (JavaScript bundle download)
- Poor SEO for dynamic content
- Layout shift after hydration
- Server-client data duplication

Trade-offs:
- Server infrastructure required
- More complex mental model
- Debugging across client/server boundary
- Caching complexity

Mental model:

Traditional SPA:
Browser → Request HTML → Get minimal HTML
       → Download large JS bundle
       → JS renders content
       → User sees content (slow)

SSR:
Browser → Request HTML → Server renders full HTML
       → User sees content immediately
       → JS downloads and "hydrates"
       → Interactivity ready

Ask your AI:
My React app loads slowly because it fetches data after the page
loads, showing spinners everywhere. Would server-side rendering
help? What would change in how I build the app?

### Evaluating AI-Assisted Development

AI coding assistants are a current example of technology requiring evaluation.

Problem they solve:
- Boilerplate code writing
- Remembering syntax and APIs
- Exploring unfamiliar codebases
- Documentation lookup

Trade-offs:
- Code quality varies
- May perpetuate bad patterns
- Over-reliance reduces learning
- Security/privacy considerations

Evaluation questions:
- Does AI assistance improve code quality or just speed?
- Are developers learning or just accepting suggestions?
- What happens when AI is unavailable?
- How do we review AI-generated code?

Ask your AI:
As an AI, what limitations should I be aware of when using AI
coding assistants? When should I trust AI suggestions versus
being sceptical?

# Your Development Career 

## The Concept First

In , you learned to evaluate technologies systematically. But technical skills alone don't build careers; they create potential. Converting that potential into opportunities requires a different skill set: professional development.

Consider two developers with identical technical abilities:

- Developer A: Strong skills, no online presence, applies to jobs cold, waits for opportunities
- Developer B: Strong skills, portfolio showing work, active in communities, creates opportunities

Developer B will have more options, better offers, and a clearer path forward, because they have made their talent visible and accessible.

This chapter isn't about self-promotion or personal branding gimmicks. It's about the practical work of building a professional presence that accurately represents your capabilities and connects you with opportunities that match your goals.

## Understanding Through Career Capital

Think of your career as a form of capital accumulation. You build different types of capital:

Technical Capital: Your skills and knowledge
- The languages you know
- The frameworks you've used
- The problems you've solved

Social Capital: Your professional relationships
- People who know your work
- Communities you contribute to
- References who vouch for you

Reputation Capital: How you're perceived
- Your portfolio and public work
- Contributions others can see
- Your professional presence

Most developers focus only on technical capital. But technical capital without social and reputation capital means opportunities don't find you, you have to chase every one.

Skills that people can see are worth more than skills they can't. A public project demonstrates capability in ways a resume cannot. Documentation you've written, code you've shared, and problems you've solved publicly all create evidence of competence.

# The AI-Era Developer 

## The Concept First

Throughout this book, you've learned web development with AI as your partner. You've used AI to explore concepts, debug problems, generate code, and build understanding. Now ask: What does it mean to be a developer in an era where AI can write code?

Job security is part of that question, but the larger part is where your value lies and which skills matter.

Consider what you've actually done in this course:

- You decided what to build
- You evaluated whether solutions were appropriate
- You understood why code worked (or didn't)
- You communicated with stakeholders (real or imagined)
- You judged trade-offs between approaches
- You adapted suggestions to your specific context

AI assisted with all of this. But AI didn't do any of this for you. The judgment, understanding, and decision-making were yours.

AI amplifies human capability rather than replacing human judgment.

## Understanding Through Partnership Evolution

Think about how your relationship with AI has evolved through this book.

Early in your journey (the Web Foundations chapters):
- AI explained concepts
- You asked "how does this work?"
- AI provided examples
- You learned fundamentals

As you grew (the platform and component chapters):
- You asked "which approach is better?"
- AI provided options with trade-offs
- You made decisions based on context
- AI helped implement your decisions

Now (the professional developer chapters):
- You ask "is this appropriate for this situation?"
- AI provides analysis
- You evaluate and judge
- The partnership is collaborative

This evolution reflects how professionals actually work with AI. Beginners need more guidance. Experts need thinking partners. The AI adapts to where you are.

## The Question Quality Principle
As you develop expertise, the quality of questions you ask AI improves. Beginner questions: "How do I centre a div?" Expert questions: "Given these constraints, what are the trade-offs between these three architectural approaches?" Better questions yield better AI partnership.

## Discovering Your AI-Era Role with Your AI Partner

### Exploration 1: What Won't Be Automated

Let's think critically about AI's limits:

Ask your AI:
What aspects of software development are unlikely to be fully
automated by AI in the foreseeable future? Be specific about why
each aspect resists automation.

Areas that remain human:

Problem definition: AI can solve problems; it struggles to identify which problems matter. "We need better user engagement" is a human judgment. AI can't determine what "better" means for your specific business.

Stakeholder communication: Clients often don't know what they want. Extracting requirements through conversation, reading non-verbal cues, and building trust remain human skills.

Ethical judgment: "Can we build this?" differs from "Should we build this?" AI can identify potential issues but can't make values-based decisions for you.

Context switching: Developers constantly shift between technical depth, business strategy, user empathy, and team dynamics. This fluid context-awareness is distinctly human.

Accountability: When something goes wrong, humans are accountable. This responsibility shapes how we approach work in ways AI doesn't replicate.

Continue the conversation:
For each area you mentioned, give me a concrete example from web
development where human judgment was essential.

### Exploration 2: Your Unique Value

Ask your AI:
I'm a developer who works with AI tools. What's my unique value?
What can I contribute that AI cannot? Be honest, don't just
reassure me.

Honest assessment of human value:

- Caring about outcomes: AI doesn't care if your project succeeds. You do.
- Understanding consequences: You understand that slow-loading pages frustrate real humans.
- Navigating ambiguity: Real requirements are messy. "Make it better" requires human interpretation.
- Building relationships: Clients hire people, not AI. Trust is human.
- Learning from failure: You remember what didn't work and why. This wisdom guides future decisions.

Continue the conversation:
What skills should I deliberately develop to remain valuable as
AI capabilities expand? What's the best investment of my learning
time?

### Exploration 3: Effective AI Partnership

Ask your AI:
How can developers work with AI most effectively? What practices
lead to good outcomes? What mistakes should I avoid?

Effective AI partnership practices:

Verify, don't trust blindly: AI makes confident-sounding errors. Always test generated code.

Understand what AI gives you: Don't use code you can't explain. If AI generates something, understand it before committing.

Iterate conversationally: One-shot prompts rarely produce optimal results. Refine through dialogue.

Provide context: AI works better with more context. Share constraints, goals, and existing code.

Stay critical: Just because AI suggests something doesn't make it right. Evaluate every suggestion.

Continue the conversation:
What are warning signs that I'm over-relying on AI? How do I
maintain my own skills while using AI assistance?

### Exploration 4: The Future Partnership

Ask your AI:
How might human-AI collaboration in software development evolve
over the next 5-10 years? What should I prepare for?

Possible evolutions:

- More capable code generation: AI will write more complex code more reliably
- Better context awareness: AI will understand your codebase more deeply
- Integration with development workflows: AI embedded in all tools
- New specialisations: AI trainers, prompt engineers, AI-human coordinators

What remains constant:

- Need for human judgment about what to build
- Requirement to understand what code does
- Importance of stakeholder communication
- Responsibility for outcomes

## From Concept to Practice

### Patterns for AI Collaboration

Throughout this course, you've developed patterns for working with AI:

Pattern 1: Exploration Before Implementation

Poor: "Write me a shopping cart component"

Better: "I need to implement a shopping cart. What approaches exist?
What are the trade-offs between storing cart state in localStorage
versus managing it in React state versus using a backend? Help me
think through this before we write code."

Explore options before committing. AI is excellent at laying out alternatives.

Pattern 2: Explain, Then Generate

Poor: "Fix this bug" [pastes code]

Better: "This component should filter products by category when the
dropdown changes. Instead, it shows all products regardless of
selection. Walk me through what the code is doing, then help me
identify where the logic is wrong."

Understanding before fixing leads to better solutions and learning.

Pattern 3: Incremental Building

Poor: "Build a complete e-commerce site"

Better:
1. "Let's start with the product data model. What fields do I need?"
2. "Now help me create a ProductCard component to display one product"
3. "Add filtering by category to the product list"
4. [Continue incrementally]

Complex systems are built incrementally. AI helps with each step.

Pattern 4: Context-Rich Requests

Poor: "Make the button look better"

Better: "This button is the primary call-to-action for signup. It's
in a hero section with a dark background image. Currently it's styled
with Tailwind as `bg-blue-500 text-white px-4 py-2`. The button feels
too small and doesn't stand out enough. Suggest improvements that
maintain accessibility."

Pattern 5: Critical Review

When AI generates code:

1. Read it: don't copy blindly
2. Understand it: can you explain each line?
3. Test it: does it actually work?
4. Evaluate it: is this the right approach?
5. Adapt it: modify it for your specific needs

### Maintaining Your Skills

AI assistance can atrophy skills if you're not careful.

Practice without AI regularly:

- Solve small problems manually first
- Use AI to check your work, not do your work
- Implement features without AI, then compare approaches

Understand fundamentals deeply:

- Know why code works, not just that it works
- Understand algorithms, not just implementations
- Learn concepts that transfer across technologies

Keep learning independently:

- Read documentation, not just AI summaries
- Work through problems yourself
- Build mental models that outlast any tool

### Quality Control for AI-Generated Code

AI code needs review. Develop a checklist:

Functionality:

- [ ] Does it actually do what you asked?
- [ ] Edge cases handled?
- [ ] Error cases handled?

Code Quality:

- [ ] Readable and maintainable?
- [ ] Consistent with project style?
- [ ] Appropriate abstraction level?

Security:

- [ ] Input validation present?
- [ ] No hardcoded secrets?
- [ ] Appropriate error exposure?

Performance:

- [ ] Obvious inefficiencies?
- [ ] Unnecessary computations?
- [ ] Appropriate data structures?

### Ethical Considerations

Working with AI raises ethical questions:

Attribution and honesty:

- Be clear about AI involvement in your work
- Don't claim AI-generated work as purely your own
- Understand your organisation's AI policies

Quality responsibility:

- You're responsible for code you commit, regardless of source
- "AI wrote it" isn't an excuse for bugs or security issues
- Review AI code as carefully as you'd review any code

Learning integrity:

- Using AI to learn is good
- Using AI to bypass learning undermines yourself
- The goal is capability, not just completion

Time saved on rote tasks should be invested in higher-value activities (design, testing, user research), not just producing more code faster.

### Team Dynamics

AI changes how teams work:

- Review processes: Now include AI-generated code review
- Skill distribution: AI democratises some capabilities
- Communication: More emphasis on clear requirements
- Training: Onboarding includes AI tool proficiency

### Client Communication

Honest framing: "We use AI tools to enhance our productivity. All AI-generated code is reviewed and tested by our developers. The AI assists; humans remain responsible for quality."

Value focus: "AI helps us explore more options and iterate faster. This means you get better solutions, not just faster delivery."

### Career Positioning

In an AI-augmented field:

- Differentiate on judgment: Anyone can generate code; not everyone can evaluate it
- Emphasise communication: Translating between humans and systems gains value
- Build domain expertise: AI is generic; domain knowledge is specific
- Demonstrate responsibility: Show you can be trusted with AI tools
